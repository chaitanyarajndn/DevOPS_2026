TFLINT
Terraform Linter
===============================================================================

Definition
----------
TFLint is an open-source Terraform linter that checks Terraform code for errors, best practice violations, and cloud provider-specific issues before infrastructure is deployed.

Simple Meaning
--------------
TFLint checks your Terraform code and tells you if it follows best practices or contains mistakes.

Purpose
-------
• Improve Terraform code quality.
• Find configuration mistakes.
• Follow Terraform best practices.
• Detect cloud provider-specific issues.
• Find issues before terraform apply.



Why was TFLint Created?
-----------------------
Terraform validates syntax and creates infrastructure, but it does not check whether your code follows best practices or cloud provider recommendations.
TFLint was created to find these issues before infrastructure is deployed.

Installation
------------
• Download the latest TFLint ZIP file from the official GitHub Releases page.
• Extract the ZIP file to C:\TOOLS.
• Add C:\TOOLS to the Windows PATH environment variable.
• Open Command Prompt or PowerShell.
• Verify the installation:
  tflint --version



Configuration File
------------------
Configuration File : .tflint.hcl
Purpose            : Store TFLint settings and plugin configuration.



Why use Configuration File?
---------------------------
• Keep the same settings for the whole team.
• Avoid writing options every time.
• Enable cloud provider plugins.
• Control scan rules from one place.



Basic Example
-------------
plugin "azurerm" {
  enabled = true
  version = "0.28.0"
  source  = "github.com/terraform-linters/tflint-ruleset-azurerm"
}



Plugin Initialization
---------------------
TFLint uses plugins to check cloud provider-specific rules (Azure, AWS, GCP).

Why run tflint --init?
----------------------
• Downloads the plugins defined in the .tflint.hcl file.
• Initializes the plugins before scanning.
• Required before running TFLint for the first time.
• Run it again only if a plugin is added or updated.

Q. Do we need to run tflint --init every time?

Ans.
No.

Run it:
• When using TFLint for the first time.
• After adding a new plugin.
• After updating an existing plugin.
• When working on a newly cloned project.

Otherwise, simply run:

tflint

Important Commands

Interview Questions
-------------------

Q. What is TFLint?
Ans.
TFLint is a Terraform linter that checks Terraform code for best practices, configuration mistakes, and provider-specific issues before deployment.

Q. Why do we use TFLint?
Ans.
To improve Terraform code quality and find issues before running terraform apply.

Q. What is the difference between terraform validate and TFLint?
Ans.
terraform validate checks Terraform syntax and configuration validity.
TFLint checks code quality, best practices, and provider-specific issues.

Q. Is TFLint a security tool?
Ans.
No.
TFLint checks code quality and best practices.
For security scanning, tools like Checkov or Trivy are used.

Q. Why do we run tflint --init?
Ans.
It downloads and initializes the plugins defined in the .tflint.hcl file before scanning.

Advanced .tflint.hcl Configuration
====================================================================

Example

plugin "azurerm" {
  enabled = true
  version = "0.28.0"
  source  = "github.com/terraform-linters/tflint-ruleset-azurerm"
}

config {
  module = true
  force  = false
}

Meaning

module = true

- Scan local Terraform modules.

force = false

- Exit with non-zero status if issues are found.
- Used to fail CI/CD pipelines.

Common Options

module = true                                  Scan local modules.

force = false                                  Fail pipeline if issues exist.

disabled_by_default = false                    Enable default rules.

rule "terraform_required_version" {
  enabled = true
}

rule "terraform_typed_variables" {
  enabled = true
}

Disable Rule

rule "terraform_typed_variables" {
  enabled = false
}

Why Disable?

- Legacy project.
- Gradual migration.
- Temporary exception.

Best Practice

Disable rules only when there is a valid business or technical reason.

Interview Questions
====================================================================

Q1. Why use TFLint when terraform validate already exists?

Answer

terraform validate checks syntax and configuration validity.

TFLint checks

- Code quality.
- Terraform best practices.
- Missing required_version.
- Missing variable types.
- Provider-specific issues.

------------------------------------------------------------

Q2. Can TFLint stop terraform apply?

Answer

No.

TFLint only reports issues.

It blocks deployment only when CI/CD is configured to fail on TFLint errors.

------------------------------------------------------------

Q3. Does TFLint modify Terraform code?

Answer

No.

It only detects issues.

Developers must fix the code manually.

------------------------------------------------------------

Q4. What does TFLint mainly check?

Answer

- Terraform best practices.
- Code quality.
- Provider-specific issues.
- Missing required_version.
- Missing variable types.

------------------------------------------------------------

Q5. Is TFLint a security tool?

Answer

No.

TFLint checks code quality.

Security scanning is performed by tools like Checkov and Trivy.

Advanced .tflint.hcl Configuration (Optional)
====================================================================

Example

plugin "azurerm" {
  enabled = true
  version = "0.28.0"
  source  = "github.com/terraform-linters/tflint-ruleset-azurerm"
}

config {
  module = true
  force  = false
}

rule "terraform_required_version" {
  enabled = true
}

rule "terraform_typed_variables" {
  enabled = true
}

------------------------------------------------------------

plugin "azurerm"

Purpose  : Load Azure-specific TFLint rules.

enabled

• Enable or disable the Azure plugin.

version

• Specifies which plugin version will be downloaded.

source

• GitHub repository from where the plugin is downloaded.

------------------------------------------------------------

------------------------------------------------------------

config {}

• The config {} block is optional.
• You do NOT need to write config {} for normal projects.
• Use config {} only when you want to change the default TFLint behavior.

Example

config {
  module = true
  force  = false
}

------------------------------------------------------------

module = true

• Default value is false.
• Use only if your project contains local Terraform modules.
• When enabled, TFLint scans the Root Module and all Local Modules.
• If your project does not use modules, you do not need this option.

Disable

config {
  module = false
}

Meaning

• Scan only the Root Module.

------------------------------------------------------------

force = false

• Default value is false.
• Return Exit Code = 1 if issues are found.
• CI/CD pipeline fails.
• Recommended for production environments.

Enable

config {
  force = true
}

Meaning

• Return Exit Code = 0 even if issues are found.
• CI/CD pipeline continues.
• Mostly used during legacy project migration.

------------------------------------------------------------

rule {}

• Most built-in TFLint rules are enabled by default.
• You do NOT need to write rule {} blocks in normal projects.
• Writing enabled = true does not change anything because the rule is already enabled.
• Use rule {} only when you want to change the default behavior.
• The most common use case is enabled = false to disable a specific check.

------------------------------------------------------------

terraform_required_version

Example

rule "terraform_required_version" {
  enabled = true
}

• No need to write this because the rule is already enabled by default.
• Use this block only if you want to disable the check.

Example

rule "terraform_required_version" {
  enabled = false
}

Meaning

• Do not check whether required_version is defined.

------------------------------------------------------------

terraform_typed_variables

Example

rule "terraform_typed_variables" {
  enabled = true
}

• No need to write this because the rule is already enabled by default.
• Use this block only if you want to disable the check.

Example

rule "terraform_typed_variables" {
  enabled = false
}

Meaning

• Do not check whether Terraform variables have a defined type.

------------------------------------------------------------

Easy Remember

plugin {}  --> Load Provider Plugin

config {}  --> Control TFLint Behavior

rule {}    --> Enable or Disable Individual Checks
