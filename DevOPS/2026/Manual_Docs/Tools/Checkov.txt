CHECKOV
Infrastructure as Code (IaC) Security Scanner
===============================================================================

Definition
----------
Checkov is an open-source Infrastructure as Code (IaC) security scanning tool developed by Bridgecrew (now part of Prisma Cloud). It scans Infrastructure as Code files to identify security misconfigurations and compliance violations before cloud infrastructure is deployed.


Simple Meaning
--------------
Checkov automatically checks your Infrastructure as Code files for security mistakes before they are deployed to the cloud.


Purpose
-------
• Detect security misconfigurations in Infrastructure as Code (IaC).
• Enforce security and compliance policies.
• Improve cloud security using Shift Left Security.
• Reduce deployment risks before infrastructure reaches production.


Why was Checkov created?
------------------------
Traditionally, cloud infrastructure was deployed first and security checks were performed later. This often resulted in security risks, compliance violations, costly fixes, and deployment delays. Checkov was created to move security checks earlier in the development lifecycle, allowing developers to detect and fix issues before deployment.


Problem it solves
-----------------
Without Checkov
---------------
• Security issues are discovered after deployment.
• Manual security reviews consume significant time.
• Misconfigured cloud resources can expose sensitive data.
• Compliance violations are detected late.
• Fixing production issues becomes expensive and risky.

With Checkov
------------
• Security issues are detected before deployment.
• Infrastructure is automatically validated against security policies.
• Compliance checks are performed during development.
• Developers receive immediate feedback.
• Secure infrastructure reaches production with lower risk.



Where is it used?
-----------------
• Local Developer Machine
• Git Repository
• Pull Request Validation
• CI/CD Pipelines
• DevSecOps Workflows
• Enterprise Cloud Deployments



Supported Infrastructure as Code
--------------------------------
• Terraform
• Terraform Plan
• Kubernetes YAML
• Helm Charts
• Dockerfile
• GitHub Actions
• Azure ARM Templates
• Azure Bicep
• AWS CloudFormation
• Serverless Framework


Shift Left Security
-------------------
Traditional Approach
Developer -> Deploy Infrastructure -> Security Scan -> Fix Issues

Shift Left Approach
Developer -> Checkov Scan -> Fix Issues -> Deploy Infrastructure



Why Shift Left?
---------------
• Security issues are cheaper to fix.
• Faster development cycles.
• Reduced deployment failures.
• Improved compliance.
• Lower production risk.

Architecture / Working
----------------------
Step 1 : Developer writes Infrastructure as Code (Terraform, Kubernetes, ARM, etc.).
Step 2 : Checkov reads every configuration file.
Step 3 : Built-in security policies are executed.
Step 4 : Custom policies (if configured) are executed.
Step 5 : Results are displayed with Pass/Fail status.
Step 6 : Developer fixes failed checks.
Step 7 : Infrastructure is deployed only after successful validation.

Built-in Rules / Policies
--------------------------
Definition
----------
Built-in rules are pre-defined security and compliance policies provided by Checkov to detect common Infrastructure as Code (IaC) security misconfigurations.

Purpose
-------
Automatically validate Infrastructure as Code against industry security best practices.

Rule Naming Convention
----------------------
CKV        = Checkov
AZURE      = Azure Provider
AWS        = Amazon Web Services
GCP        = Google Cloud Platform
K8S        = Kubernetes
Number     = Unique Rule ID

Example
-------
CKV_AZURE_35

CKV        = Checkov
AZURE      = Azure
35         = Rule Number

Common Built-in Rules
---------------------
CKV_AZURE_9    : Secure Transfer should be enabled.
CKV_AZURE_33   : Public Network Access should be restricted.
CKV_AWS_20     : S3 Bucket security validation.
CKV_K8S_21     : Kubernetes security validation.

How Built-in Rules Work
------------------------
Terraform File
      │
      ▼
Checkov Loads Built-in Rules
      │
      ▼
Validates Resource Configuration
      │
      ▼
PASS or FAIL
      │
      ▼
Displays Scan Report

Benefits
--------
• Hundreds of ready-to-use security rules.
• No manual policy creation required.
• Regularly updated by Checkov.
• Supports Azure, AWS, GCP, Kubernetes and other IaC platforms.

Custom Rules / Policies
------------------------
Definition
----------
Custom rules allow organizations to create their own security and compliance policies based on internal standards and business requirements.

Why create Custom Rules?
------------------------
• Organization-specific security standards.
• Internal compliance requirements.
• Customer security policies.
• Regulatory requirements.
• Governance standards.

Supported Languages
-------------------
• Python
• YAML

Common Enterprise Use Cases
---------------------------
• Enforce mandatory resource tags.
• Restrict specific Azure regions.
• Allow only approved VM sizes.
• Block Public IPs in Production.
• Apply company naming conventions.
• Enforce Minimum TLS Version.

Enterprise Example
------------------
Company Policy
--------------

• HTTPS Only Enabled
• Secure Transfer Enabled
• Minimum TLS 1.2
• Mandatory Tags

Result
------
Deployment is allowed only when both Built-in Rules and Custom Rules pass successfully.

Built-in vs Custom Rules
------------------------
Built-in Rules
• Developed and maintained by Checkov.
• Covers common cloud security best practices.
• Ready to use.

Custom Rules
• Developed by the organization.
• Covers internal security and compliance requirements.
• Fully customizable.

Q. What are Built-in Rules?

Ans.

[Interview]

Q. Which command scans the current directory?

Ans.
• Use "checkov -d ." to scan all supported Infrastructure as Code files in the current directory.
• This is the most commonly used command during local development and CI/CD pipelines.

[Interview]

Q. What is the difference between --check and --skip-check?

Ans.
• --check executes only the specified security rule during the scan.
• --skip-check ignores the specified security rule while executing all remaining rules.

[Interview]

Q. What is the purpose of --soft-fail?

Ans.
• It reports security violations but returns Exit Code 0, allowing the CI/CD pipeline to continue.
• It is commonly used during the initial adoption phase to identify issues without blocking deployments.

[Interview]

Q. Why do we generate JSON or SARIF reports?

Ans.
• JSON reports are used for automation, integrations and further processing by other tools.
• SARIF reports integrate with security dashboards and platforms like GitHub Advanced Security.

Best Practices
--------------
• Scan code before every commit.
• Integrate Checkov into every CI/CD pipeline.
• Fix High and Critical findings immediately.
• Do not ignore security rules without valid business justification.
• Keep Checkov updated to receive the latest security policies.
• Store custom policies in version control.
• Review reports before every production deployment.
• Re-run scans after every code change.

Advantages
----------

-----------
• Cannot fix security issues automatically.
• May produce false positives.
• Requires developers to understand security recommendations.

• Focuses only on Infrastructure as Code security.

Choose tfsec when:
• Working only with Terraform.
• Lightweight Terraform security scanning is sufficient.

Advanced Interview Questions

[Interview]

Q. What is Shift Left Security?

Ans.
• Shift Left Security means performing security validation early in the Software Development Lifecycle instead of after deployment.
• Checkov helps implement Shift Left by scanning Infrastructure as Code before cloud resources are deployed.

[Interview]

Q. Does Checkov fix security issues automatically?

Ans.
• No. Checkov only identifies security misconfigurations and provides recommendations.
• Developers must update the Infrastructure as Code and run the scan again.

[Interview]

Q. Can Checkov be integrated into CI/CD?

Ans.
• Yes. Checkov integrates with Azure DevOps, GitHub Actions, Jenkins, GitLab CI/CD and other CI/CD platforms.
• It automatically validates Infrastructure as Code before deployment.

[Interview]

Q. What happens if Checkov finds security issues?

Ans.
• Checkov reports the failed security checks along with recommendations.
• Depending on pipeline configuration, deployment may continue (Soft Fail) or stop (Hard Fail).
