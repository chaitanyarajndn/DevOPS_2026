1. FIRST, UNDERSTAND THE PROBLEM
============================================================

Imagine you work on an enterprise application called ICMS
(Insurance Claims Management System).

The application has three main components:

    Frontend  : Angular
    Backend   : .NET / ASP.NET Core
    Database  : Azure SQL Database

A customer submits an insurance claim through the application.

What happens next?

    Customer submits claim
              |
              v
       .NET Backend
              |
              v
       Azure SQL Database
              |
              v
       Claim is saved

So far, everything is fine.

BUT NOW THE BUSINESS WANTS MORE FEATURES.

Whenever a new claim is submitted:

    1. Save the claim in the database.
    2. Send a confirmation email to the customer.
    3. Notify the claims team in Microsoft Teams.
    4. Check whether the claim requires manual approval.
    5. Send the claim details to another business system.

Now we have multiple operations involving different systems.

QUESTION:
Who will execute all these additional operations?


============================================================
2. THE OLD WAY: WRITE CODE FOR EVERYTHING
============================================================

One approach is to write additional code in the .NET backend.

For example:

    Customer submits claim
              |
              v
       .NET Backend
              |
              +----> Save claim in Azure SQL
              |
              +----> Send confirmation email
              |
              +----> Notify Teams
              |
              +----> Check approval requirements
              |
              +----> Call external business system

This approach can work.

But as the application grows, some problems may appear.

PROBLEM 1: MORE CODE TO MAINTAIN
--------------------------------
Developers must write and maintain code for multiple integrations.

PROBLEM 2: DIFFERENT SYSTEMS
----------------------------
Email, Teams, databases and external applications have different
APIs, authentication methods and communication requirements.

PROBLEM 3: FAILURE HANDLING
---------------------------
What happens if the email service is temporarily unavailable?

The application may need retry logic, error handling and logging.

PROBLEM 4: BACKGROUND PROCESSING
--------------------------------
Some tasks should happen in the background rather than delay
the customer's claim submission.

PROBLEM 5: INFRASTRUCTURE
-------------------------
Additional code may need hosting, monitoring and scaling.

IMPORTANT:
These problems do not mean that .NET is bad.

Developers can solve them using .NET and other services.
However, doing everything manually can increase development
and maintenance effort.


============================================================
3. THE AZURE SOLUTION
============================================================

Microsoft Azure provides managed services that help solve
different parts of these problems.

Two of these services are:

    1. Azure Logic Apps
    2. Azure Functions

They solve related problems, but they are NOT the same service.


------------------------------------------------------------
A. AZURE LOGIC APPS
------------------------------------------------------------

PROBLEM:
How can we connect different systems and automate a sequence
of business operations without writing all the integration
code ourselves?

SOLUTION:
Azure Logic Apps.

Think of Logic Apps as a WORKFLOW AUTOMATION SERVICE.

You define what should happen and in what order.

ICMS EXAMPLE:

    New claim submitted
            |
            v
    Logic Apps detects the event
            |
            v
    Send confirmation email
            |
            v
    Notify claims team in Teams
            |
            v
    Check approval requirement
            |
            v
    Continue the appropriate workflow

You can build workflows using a visual designer and
connectors for supported services.

You do not need to write all the integration code yourself.

KEY POINTS:
    - Automates business workflows.
    - Connects different applications and services.
    - Supports triggers, actions and conditions.
    - Provides connectors for many common systems.
    - Azure manages the underlying workflow infrastructure.

Think:
LOGIC APPS = CONNECT SYSTEMS + AUTOMATE WORKFLOWS.

B. AZURE FUNCTIONS
------------------------------------------------------------

PROBLEM:
What if a task requires custom programming logic?


ICMS = Insurance Claims Management System

IMPORTANT: HOW TO UNDERSTAND THESE FLOWCHARTS
============================================================
1. A trigger starts a function. Examples include an HTTP request, timer, message or supported storage event.
2. Azure Function executes the custom code written by the developer.
3. The function produces a result, updates a resource or sends a message, depending on its implementation.
4. Other components can use that result to continue the business process.
5. The function does not need to manage the entire ICMS workflow.
REMEMBER:
Azure Function = TRIGGER → EXECUTE CUSTOM CODE → PRODUCE RESULT
Logic Apps or .NET Backend = Can coordinate the remaining business steps.
============================================================

KEY POINTS:
    - Runs your custom code.
    - Supports languages such as C#, JavaScript and Python.
    - Can execute code when an event occurs.
    - Can respond to HTTP requests or scheduled events.
    - Can process messages and files.

Think:
AZURE FUNCTIONS = RUN CUSTOM CODE WHEN NEEDED.

4. WHY ARE THEY CALLED PAAS SERVICES?
============================================================

PaaS = Platform as a Service.

Let's compare two approaches.

OPTION A: HOST YOUR OWN APPLICATION ON A VIRTUAL MACHINE
--------------------------------------------------------

You may be responsible for:

    Virtual machine
         |
         +--> Operating system maintenance
         +--> Runtime installation
         +--> Application deployment
         +--> Security patching
         +--> Capacity planning
         +--> Application monitoring

OPTION B: USE A MANAGED SERVICE
-------------------------------

For Logic Apps:

    Configure your workflow
             |
             v
    Azure runs the workflow

For Azure Functions:

    Write and deploy your code
             |
             v
    Azure executes the function

Azure manages much of the underlying infrastructure.

However, you are still responsible for your workflow or code,
configuration, permissions, monitoring and application logic.

IMPORTANT:
PaaS does NOT mean that Azure manages absolutely everything.

It means Azure takes responsibility for much of the platform
and infrastructure management.

Also, serverless services are not necessarily free.
Costs depend on the service, hosting plan, usage and resources.


============================================================
5. WHAT DOES SERVERLESS MEAN?
============================================================

You will frequently hear this term when learning Logic Apps
and Azure Functions.

Serverless does NOT mean that there are no servers.

Servers still exist.

Azure manages the underlying infrastructure so that you can
focus more on your workflow or code instead of managing
servers directly.

For example:

    WITHOUT A MANAGED SERVICE
    -------------------------
    Arrange hosting
         |
    Configure runtime
         |
    Deploy code
         |
    Manage capacity

    WITH AZURE FUNCTIONS
    --------------------
    Write code
         |
    Configure the function
         |
    Deploy
         |
    Azure executes the code

Some hosting plans can automatically scale according to
workload demand.

Certain plans can also charge according to execution or usage.
Other plans have different pricing models.

Therefore, SERVERLESS DOES NOT ALWAYS MEAN PAY ONLY WHEN CODE RUNS.

6. LOGIC APPS VS FUNCTIONS: THE BASIC DIFFERENCE
============================================================

AZURE LOGIC APPS
----------------
Purpose:
Connect systems and automate workflows.

Example:
When a claim is submitted:
    1. Send an email.
    2. Notify Teams.
    3. Request approval.
    4. Update another system.

AZURE FUNCTIONS
---------------
Purpose:
Execute custom code.

Example:
When a claim is submitted:
    1. Read the claim details.
    2. Calculate a risk score.
    3. Apply custom business rules.
    4. Return the result.

CAN THEY WORK TOGETHER?
-----------------------
YES.

For example:

AZURE LOGIC APPS + AZURE FUNCTIONS
ICMS (Insurance Claims Management System) — Real-World Example
SCENARIO:
A customer submits a vehicle insurance claim and uploads repair documents. ICMS needs to validate the uploaded documents, calculate the estimated claim amount, and notify the customer whether the documents are valid or further documents are required.
SOLUTION: AZURE LOGIC APPS + AZURE FUNCTIONS
Azure Logic Apps manages the workflow and connects the required services. Azure Functions executes the custom code to validate documents and calculate the estimated claim amount.

WHO DOES WHAT?
============================================================
AZURE LOGIC APPS:
- Manages the sequence of workflow steps.
- Calls the Azure Function.
- Checks the returned result and selects the next action.
- Connects to supported services to send emails or notifications.
AZURE FUNCTIONS:
- Executes the custom document-validation code.
- Calculates the estimated payout when given the required inputs.
- Returns the results to Logic Apps.
.NET BACKEND:
- Handles the ICMS application's core business operations.
- Saves claim details and updates database records as required.
- Provides the claim data needed by the workflow.
IMPORTANT:
The example assumes the Logic Apps workflow is configured to call the function and handle its result. The function does not automatically validate documents or calculate payouts; developers must implement the required rules in code.
REMEMBER:
LOGIC APPS = MANAGES THE WORKFLOW
AZURE FUNCTIONS = EXECUTES CUSTOM CODE
BOTH TOGETHER = AUTOMATE THE BUSINESS PROCESS
