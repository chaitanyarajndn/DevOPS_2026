

07 + 08) SERVICE ENDPOINT — ADVANTAGES, LIMITATIONS & SERVICE ENDPOINT POLICY
══════════════════════════════════════════════════════════════════════════════

SERVICE ENDPOINT — ADVANTAGES
══════════════════════════════════════════════════════════════════════════════

1) Better Network Security
→ You can allow an Azure PaaS resource to accept traffic only from specific VNet/subnets.

2) Azure Backbone Connectivity
→ Traffic from VNet to the Azure service stays on the Microsoft Azure backbone instead of going through the public Internet.

3) Simple Configuration
→ Enable the required service directly on the subnet; no NAT Gateway, VPN Gateway or extra network appliance is required.

4) No Private IP Management
→ You don't need to reserve public IPs or manage IP-based firewall rules for identifying the VNet source.

5) Optimal Routing
→ Azure creates a service-specific route so traffic goes directly from the VNet to the Azure service.

6) Low Management Overhead
→ Service Endpoints are easy to configure and maintain because there is no separate endpoint resource/NIC to manage.

7) No Additional Service Endpoint Cost
→ Azure does not charge separately for using Service Endpoints; normal charges for the Azure service still apply.


SERVICE ENDPOINT — LIMITATIONS / DISADVANTAGES
══════════════════════════════════════════════════════════════════════════════

1) No Private IP for PaaS
→ The Azure service still uses its public endpoint; Service Endpoint does not create a private IP for the PaaS resource.

2) No Private On-Premises Connectivity
→ Service Endpoints cannot provide private access from on-premises networks; use Private Endpoint for this requirement.

3) Public Endpoint Cannot Be Disabled
→ With Service Endpoint, the PaaS service still has a public endpoint; Private Endpoint can provide access without using the public endpoint.

4) DNS Usually Does Not Change
→ The service FQDN continues to resolve to the Azure service's public IP; there is no private DNS mapping like Private Endpoint.

5) Limited to Supported Azure Services
→ Service Endpoints work only with Azure services that support Service Endpoints.

6) Not Resource-Specific by Default
→ A Service Endpoint enables access to the service type; for Storage, use a Service Endpoint Policy when you need to restrict access to specific Storage Accounts.

7) Not a Replacement for Authentication
→ Service Endpoint provides network-level access control; Entra ID, RBAC, keys, or other authentication is still required.

8) Source IP Changes
→ After enabling the endpoint, service traffic uses the subnet resource's private IP instead of the previous public IPv4 source, so existing IP firewall rules may need updating.

INTERVIEW SHORT ANSWER
══════════════════════════════════════════════════════════════════════════════

"Service Endpoints are simple and low-maintenance because they provide direct
Azure backbone connectivity and subnet-level network restriction without
creating a private IP or additional network appliance. The main limitations
are that the PaaS service still uses a public endpoint, private on-premises
access is not provided, and it works only with supported Azure services."

Microsoft Learn confirms these benefits and limitations. :contentReference[oaicite:0]{index=0}

3) SERVICE ENDPOINT POLICY — WHY?
──────────────────────────────────────────────────────────────────────────────
Normal Service Endpoint:

snet-web01
   ↓
Microsoft.Storage
   ↓
Storage Account A ✓
Storage Account B ✓
Storage Account C ✓

Problem:
Agar subnet ko Storage Service Endpoint diya hai, to subnet se
multiple Storage Accounts tak access possible ho sakta hai, depending
on Storage network rules.

Service Endpoint Policy gives more granular control.

──────────────────────────────────────────────────────────────────────────────
4) SERVICE ENDPOINT POLICY KYA KARTI HAI?
──────────────────────────────────────────────────────────────────────────────
Service Endpoint Policy
        ↓
Subnet se Azure Storage traffic filter
        ↓
ONLY specified Storage Accounts allowed

Example:

snet-web01
   │
   ├── Microsoft.Storage
   │
   └── Service Endpoint Policy
             │
             ├── novatfstatefiles ✓ ALLOW
             ├── storage-dev ✓ ALLOW
             └── unknown-storage ✗ DENY

So:

Service Endpoint
→ "Subnet ko Azure Storage access allowed hai"

Service Endpoint Policy
→ "Subnet ko KIN specific Storage Accounts tak access allowed hai"

──────────────────────────────────────────────────────────────────────────────
5) POLICY KAHAN CONFIGURE HOTI HAI?
──────────────────────────────────────────────────────────────────────────────
Service Endpoint Policy
        ↓
ASSOCIATED WITH SUBNET

Example:

vnet-web
   ↓
snet-web01
   ├── Service Endpoint → Microsoft.Storage
   └── Service Endpoint Policy → storage-policy

Policy definition me allowed Storage Account ka RESOURCE ID specify
kiya ja sakta hai.

7) IMPORTANT POLICY BEHAVIOR
──────────────────────────────────────────────────────────────────────────────
Once a Service Endpoint Policy is attached:

ONLY resources listed in the policy are allowed
        ↓
Other Storage resources
        ↓
DENIED

Therefore:

Before applying policy:
→ Check which Storage Accounts the application actually needs.

Otherwise:
→ Required Storage dependency can suddenly stop working.

Microsoft specifically warns to identify required service resources before
associating the policy with the subnet. :contentReference[oaicite:1]{index=1}

──────────────────────────────────────────────────────────────────────────────
8) SERVICE ENDPOINT vs SERVICE ENDPOINT POLICY
──────────────────────────────────────────────────────────────────────────────
SERVICE ENDPOINT
→ Subnet → Microsoft.Storage
→ Enables service connectivity
→ Network-level restriction

SERVICE ENDPOINT POLICY
→ Subnet → Policy → Specific Storage Resources
→ Granular allow-list
→ Helps prevent unwanted Storage access / data exfiltration

──────────────────────────────────────────────────────────────────────────────
9) IMPORTANT LIMITATIONS OF SERVICE ENDPOINT POLICY
──────────────────────────────────────────────────────────────────────────────
• Currently focused on Azure Storage
• Cannot be used for on-premises → Azure service traffic
• Policy applies to the subnet where it is associated
• Service Endpoint must already be enabled for the service
• Managed Azure services have support limitations
• No additional charge for the policy itself

Microsoft Learn currently states that Service Endpoint Policies are
generally available for Azure Storage. :contentReference[oaicite:2]{index=2}

──────────────────────────────────────────────────────────────────────────────
INTERVIEW ANSWER
──────────────────────────────────────────────────────────────────────────────
"Service Endpoints provide subnet-level access to supported Azure services
over the Azure backbone. They are simple to configure and don't require
additional NAT or gateway infrastructure. The main limitation is that they
don't provide a private IP for the PaaS service and don't support
on-premises access.

For Azure Storage, if I need more granular control, I can use a Service
Endpoint Policy on the subnet. The policy allows me to specify which
Storage Accounts the subnet can access. So Service Endpoint provides the
service connectivity, while Service Endpoint Policy provides a more
specific allow-list for Storage resources."
