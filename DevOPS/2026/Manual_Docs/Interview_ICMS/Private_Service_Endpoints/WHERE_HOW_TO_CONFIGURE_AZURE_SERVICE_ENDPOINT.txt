QUESTION 03 → WHERE + HOW TO CONFIGURE AZURE SERVICE ENDPOINT?
════════════════════════════════════════════════════════════════════════════════════════════════════════════════════════════

──────────────────────────────────────────────────────────────────────────────

1) WHERE DO WE CONFIGURE SERVICE ENDPOINT?
──────────────────────────────────────────────────────────────────────────────
Service Endpoint is configured on the AZURE SUBNET.

VNet  ✗
VM    ✗
NIC   ✗
PaaS Resource ✗
SUBNET ✓  → Service Endpoint is enabled here

Example:
VNet:       vnet-web
Subnets:    snet-web01
            snet-web02
            AzureBastionSubnet

If Storage access is required from snet-web01:

vnet-web
   │
   ├── snet-web01  → Microsoft.Storage ✓
   ├── snet-web02  → No endpoint
   └── AzureBastionSubnet → No endpoint

Microsoft confirms that service endpoints are enabled on the subnet. :contentReference[oaicite:0]{index=0}
──────────────────────────────────────────────────────────────────────────────

2) WHAT DO WE SELECT WHILE CONFIGURING IT?
──────────────────────────────────────────────────────────────────────────────
On the subnet:

Service Endpoints
      ↓
Select the Azure service
      ↓
Example:
Microsoft.Storage

Common examples:
Microsoft.Storage
Microsoft.Sql
Microsoft.KeyVault
Microsoft.ServiceBus
Microsoft.EventHub
etc.

IMPORTANT:
You select the SERVICE TYPE, not the specific Storage Account / SQL Database.

Example:
snet-web01 → Microsoft.Storage

This means:
"Resources running in this subnet can use the Azure Storage service through
a Service Endpoint."

It does NOT mean:
"Only novatfstatefiles is automatically allowed."

The target PaaS resource must also have the appropriate network rule. :contentReference[oaicite:1]{index=1}
──────────────────────────────────────────────────────────────────────────────

3) HOW TO CONFIGURE FROM AZURE PORTAL?
──────────────────────────────────────────────────────────────────────────────
PORTAL FLOW:

Azure Portal
   ↓
Virtual Networks
   ↓
vnet-web
   ↓
Subnets
   ↓
snet-web01
   ↓
Service Endpoints
   ↓
Services → Microsoft.Storage
   ↓
Save

That's the SERVICE ENDPOINT side.

For Storage, there is one more important configuration:

Storage Account
   ↓
Networking
   ↓
Public network access
   ↓
Enabled from selected networks
   ↓
Virtual networks
   ↓
Add existing virtual network
   ↓
vnet-web
   ↓
snet-web01
   ↓
Save

So practically:

SUBNET SIDE
snet-web01
   → Microsoft.Storage
   → Service Endpoint enabled
             +
STORAGE SIDE
novatfstatefiles
   → Allow vnet-web / snet-web01
             =
ACCESS ALLOWED

Microsoft Learn explicitly shows both enabling the service endpoint on the
subnet and adding the subnet as a Storage virtual network rule. :contentReference[oaicite:2]{index=2}


──────────────────────────────────────────────────────────────────────────────
3) NETWORK IDENTIFIER — IMPORTANT
──────────────────────────────────────────────────────────────────────────────
Network Identifier is part of the NEWER "Standard Service Endpoint"
capability.

Network Identifier = PUBLIC IP ADDRESS associated with the Service Endpoint.

Flow:
Subnet
  ↓
Standard Service Endpoint
  ↓
Network Identifier (Public IP)
  ↓
PaaS Resource / Network Security Perimeter

IMPORTANT:
• It is used for IDENTIFICATION of Service Endpoint traffic.
• It is NOT used as the routing IP.
• One Network Identifier can represent multiple VNets/subnets.
• It works with Network Security Perimeter (NSP).
• Supported services currently include Storage, Key Vault, SQL Database
  and Cosmos DB.

Microsoft Learn currently lists Standard Service Endpoint as
PUBLIC PREVIEW → not recommended for production workloads. :contentReference[oaicite:1]{index=1}

5) TERRAFORM CONFIGURATION
──────────────────────────────────────────────────────────────────────────────
Service Endpoint is configured in the AZURERM_SUBNET resource:

resource "azurerm_subnet" "snet_web01" {
  name                 = "snet-web01"
  resource_group_name  = "..."
  virtual_network_name = "vnet-web"

  address_prefixes = [
    "10.77.1.0/24"
  ]

  service_endpoints = [
    "Microsoft.Storage"
  ]
}

Key point:

service_endpoints → belongs to azurerm_subnet

NOT:
azurerm_virtual_network
azurerm_storage_account
azurerm_network_interface
──────────────────────────────────────────────────────────────────────────────

6) STORAGE ACCOUNT SIDE — IMPORTANT
──────────────────────────────────────────────────────────────────────────────
For Storage network restriction, the Storage Account must allow the subnet.

Conceptually:

Storage Account
   │
   ├── Public network access → Enabled
   │
   ├── Access scope → Selected networks
   │
   └── Virtual network rules
          └── vnet-web / snet-web01 ✓

Microsoft Learn states that Storage network rules control access to the
Storage public endpoint and that the allowed subnet must also have the
appropriate Storage service endpoint enabled. :contentReference[oaicite:4]{index=4}
──────────────────────────────────────────────────────────────────────────────

7) IMPORTANT: "PUBLIC NETWORK ACCESS = ENABLED" — WHY?
──────────────────────────────────────────────────────────────────────────────
With SERVICE ENDPOINT:

Storage still uses its normal service endpoint/public endpoint.

Therefore:

Public Network Access
        ↓
      ENABLED
        ↓
Enabled from SELECTED NETWORKS
        ↓
Only approved networks can access

Do NOT confuse:

Enabled from selected networks
        ≠
Enabled from all networks

And:

Public Network Access = Disabled
        ↓
typically means you are moving toward
PRIVATE ENDPOINT / private connectivity model.

Microsoft documents these as separate network-access choices. :contentReference[oaicite:5]{index=5}
──────────────────────────────────────────────────────────────────────────────

8) WHAT ABOUT IPv4 ADDRESSES?
──────────────────────────────────────────────────────────────────────────────
Storage Account → Networking → IP network rules

Use this when you want to allow a PUBLIC IP/CIDR.

Example:

Office Public IP
203.0.113.10
      ↓
Storage Account
      ↓
IPv4 rule → Allow

For your Service Endpoint requirement:

IPv4 Addresses → LEAVE EMPTY

unless you ALSO need access from:
• Office public IP
• Home/laptop public IP
• Other external public network

Microsoft treats IP rules and virtual-network rules as separate network
access mechanisms. :contentReference[oaicite:6]{index=6}
──────────────────────────────────────────────────────────────────────────────

9) WHAT ABOUT "RESOURCE INSTANCES"?
──────────────────────────────────────────────────────────────────────────────
Resource Instance Rules are for allowing access from specific Azure
resource instances that aren't being handled by subnet/IP rules.

For your current:

Terraform backend
+
Service Endpoint
+
vnet-web / snet-web01

→ Resource Instances = LEAVE EMPTY

Don't configure it unless you have a specific Azure resource that needs
this type of access. :contentReference[oaicite:7]{index=7}
──────────────────────────────────────────────────────────────────────────────

10) WHAT ABOUT "ALLOW TRUSTED MICROSOFT SERVICES"?
──────────────────────────────────────────────────────────────────────────────
This is an EXCEPTION.

It allows certain trusted Azure services to access the Storage Account
when those services operate outside your VNet/network boundary.

For your current Service Endpoint setup:

"Allow trusted Microsoft services..."
→ KEEP UNCHECKED initially

Enable it only when a specific Azure service dependency requires it.

Don't enable it just because it is available.

Microsoft describes this as a network security exception, separate from
VNet rules. :contentReference[oaicite:8]{index=8}
──────────────────────────────────────────────────────────────────────────────

11) VERY IMPORTANT PRACTICAL POINT — TERRAFORM BACKEND
──────────────────────────────────────────────────────────────────────────────
Your Storage Account is being used as:

Terraform Backend
      ↓
novatfstatefiles
      ↓
tfstate container
      ↓
terraform.tfstate

Before restricting Storage networking, ASK:

"Where is Terraform actually running?"

CASE 1:
Terraform/Azure DevOps self-hosted agent
        ↓
inside vnet-web / snet-web01
        ↓
Service Endpoint works ✓

CASE 2:
Terraform running from your local laptop
        ↓
NOT inside snet-web01
        ↓
Service Endpoint rule does NOT apply to laptop ✗

CASE 3:
Terraform agent somewhere else
        ↓
not an allowed subnet
        ↓
Storage network rule blocks it ✗

This is a very important production consideration because changing the
Storage firewall/network rules can break Terraform backend access. Microsoft
also warns to ensure required access before changing the default network
action to Deny. :contentReference[oaicite:9]{index=9}
──────────────────────────────────────────────────────────────────────────────

12) SERVICE ENDPOINT ≠ PRIVATE ENDPOINT
──────────────────────────────────────────────────────────────────────────────
SERVICE ENDPOINT:

Subnet
  ↓
Service Endpoint
  ↓
Azure backbone
  ↓
PaaS public endpoint
  ↓
Storage

No private IP is created for Storage.
No Private Endpoint NIC is created.

PRIVATE ENDPOINT:

VNet/Subnet
   ↓
Private Endpoint NIC
   ↓
Private IP
   ↓
PaaS resource

Microsoft currently recommends Azure Private Link/private endpoints for
secure and private access to Azure platform services. :contentReference[oaicite:10]{index=10}
──────────────────────────────────────────────────────────────────────────────

13) INTERVIEW ANSWER — WHERE + HOW?
──────────────────────────────────────────────────────────────────────────────
"Service Endpoint is configured at the subnet level in an Azure Virtual
Network. I go to the required subnet, enable the required service such as
Microsoft.Storage, and save the configuration. For a PaaS resource like
Azure Storage, I also configure the resource's network rules to allow that
specific VNet and subnet. So the configuration has two sides: the subnet
side, where I enable the Service Endpoint, and the PaaS side, where I
authorize that subnet. The traffic then uses the Azure backbone network
while the PaaS service still uses its service endpoint."

──────────────────────────────────────────────────────────────────────────────
QUICK REVISION
──────────────────────────────────────────────────────────────────────────────
WHERE?
→ Azure VNet → SUBNET

HOW?
→ Subnet → Service Endpoints → Select service
→ Example: Microsoft.Storage

FOR STORAGE?
→ Enable Microsoft.Storage on subnet
+
→ Storage Account → Networking → Selected networks
→ Add VNet + Subnet

YOUR CASE:
vnet-web
   ↓
snet-web01
   ↓
Microsoft.Storage ✓
   ↓
novatfstatefiles
   ↓
Allow vnet-web / snet-web01 ✓

REMEMBER:
Service Endpoint = SUBNET configuration
Storage VNet Rule = PaaS-side authorization
Public Network Access = ENABLED + Selected Networks
Private Endpoint = different architecture
