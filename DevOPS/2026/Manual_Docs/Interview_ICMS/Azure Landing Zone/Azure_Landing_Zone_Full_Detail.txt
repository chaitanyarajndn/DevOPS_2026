1. WHAT IS AZURE LANDING ZONE?
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────
Azure Landing Zone (ALZ) = A proven and flexible Azure architecture for GOVERNING, SECURING and SCALING
a multi-subscription Azure environment.

Simple definition:
    "Landing Zone is the enterprise foundation on which Azure workloads are deployed."

It provides:
    Identity + Access
    Governance
    Security
    Networking + Connectivity
    Management + Monitoring
    Resource Organization
    Platform Automation / DevOps

IMPORTANT:
    Landing Zone ≠ VNet
    Landing Zone ≠ Subscription
    Landing Zone ≠ Hub-Spoke
    Landing Zone ≠ Terraform

Landing Zone is the COMPLETE operating/foundation architecture.
Hub-Spoke or Virtual WAN = networking topology used within that architecture.
Terraform = one way to implement/automate it.

Microsoft Cloud Adoption Framework (CAF):
    Plan → Ready → Adopt → Govern → Manage

Landing Zone primarily belongs to the READY phase.

2. WHY DO WE NEED A LANDING ZONE?
─────────────────────────────────────────────────────────────────────────────

Without Landing Zone:

    Team A → creates VNet
    Team B → creates another VNet differently
    Team C → gives excessive RBAC
    Team D → deploys resources in unapproved region
    Team E → doesn't configure monitoring

Result:
    Configuration drift
    Security gaps
    Inconsistent governance
    Difficult operations
    Difficult scaling

With Landing Zone:

    Central Foundation
          ↓
    Governance + Security + Networking + Identity + Management
          ↓
    Standardized workload environments
          ↓
    Consistent Azure deployments

Main objective:
    "Give application teams enough freedom to manage their workloads while
     keeping enterprise security and governance guardrails."

4. PLATFORM LANDING ZONE
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

Platform Landing Zone establishes the organization's Azure foundation.

Main responsibilities:

    ├── Management Group hierarchy
    ├── Governance
    ├── Identity
    ├── Connectivity
    ├── Security
    ├── Management / Monitoring
    └── Application Landing Zone distribution

Microsoft guidance:
    Most organizations should have ONE Platform Landing Zone per
    Microsoft Entra tenant.

Platform team:
    → Builds foundation
    → Defines guardrails
    → Provides shared services
    → Creates/provisions Application Landing Zones
    → Maintains centralized capabilities

IMPORTANT:
    Platform does NOT necessarily own every application resource.
    Workload teams own and operate their application resources.

5. APPLICATION LANDING ZONE
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

Each WORKLOAD has a SINGLE Application Landing Zone.

An Application Landing Zone contains ALL environments required by that workload.

Example:

    ICMS WORKLOAD
         │
         └── APPLICATION LANDING ZONE
                 │
                 ├── DEV
                 ├── TEST / QA
                 └── PROD

Each environment can have:
    → One subscription
    OR
    → Multiple subscriptions

Multiple subscriptions are used only when justified by:
    → Workload requirements
    → Team ownership boundaries
    → Security/isolation requirements
    → Organizational boundaries
    → Azure subscription limits

Application Landing Zone contains:
    → Azure resources owned/operated by workload team
    → Across all workload environments

6. PLATFORM vs APPLICATION LANDING ZONE
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

PLATFORM LANDING ZONE                  APPLICATION LANDING ZONE
─────────────────────                  ─────────────────────────
Enterprise foundation                  Workload environment
Platform team                           Workload/application team
Central governance                      Workload resources
Central connectivity                    Application networking
Central security                        AKS/VM/App Service/etc.
Central monitoring                      Application services
Shared capabilities                     Application-specific resources
Creates ALZs                            Consumes platform capabilities

INTERVIEW:
    "Platform Landing Zone provides the foundation and guardrails;
     Application Landing Zone hosts the actual workload."

              │
              ├── Sandbox
              │

IMPORTANT:
    "Corp", "Online" and "Local" are workload categories,
    NOT DEV/QA/PROD management groups.

    Landing Zones
       ├── DEV
       ├── QA
       └── PROD

    Landing Zones
       └── Corp

            ├── Workload-QA

ideally around 3–4 levels, to reduce complexity.

13. MANAGEMENT GROUP DESIGN RULES
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

GOOD:

    Management Groups = Governance boundaries

BAD:

    Management Groups = Exact copy of company org chart

Avoid:

    Root
      ↓
    Country
      ↓
    Department
      ↓
    Business Unit
      ↓
    Team
      ↓
    Application
      ↓
    Environment

This creates unnecessary complexity.

Use Management Groups mainly for:
    → Policy
    → Compliance
    → Governance
    → Workload classification

Use subscriptions/resource groups for:
    → Workload ownership
    → Environment separation
    → Application boundaries

Microsoft guidance:
    Keep hierarchy reasonably flat.
    Ideally no more than 3–4 management group levels.

14. AZURE POLICY
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

Azure Policy = Governance mechanism used to AUDIT and/or ENFORCE
resource configuration.

Examples:

    Allowed Locations
    Required Tags
    Allowed SKUs
    Require HTTPS
    Restrict public IPs
    Require diagnostic settings
    Security configuration
    Regulatory requirements

Policy effects commonly include:

    Audit
    Deny
    Modify
    Append
    DeployIfNotExists

Typical flow:

    Management Group
          ↓
    Policy Assignment
          ↓
    Subscription
          ↓
    Resource Group
          ↓
    Resource

Policy inheritance allows common rules to be applied consistently.

15. RBAC vs AZURE POLICY
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

RBAC = WHO can perform an ACTION?

Azure Policy = WHAT configuration is allowed/required?

Example:

    RBAC:
        Developer → Contributor on Application Subscription

    Policy:
        Resources → Only approved Azure regions

Think:

    RBAC  → Permission
    Policy → Governance

IMPORTANT:
    Application teams should normally receive RBAC at:
        Subscription or Resource Group

    NOT normally at:
        Management Group

Why?
    Management Group RBAC can give excessive inherited access.

Platform teams may have broader management-group RBAC when required,
but privileged access should be tightly controlled.

16. IDENTITY & ACCESS MANAGEMENT
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

Identity is a PRIMARY security boundary.

Main components:

    Microsoft Entra ID
    Azure RBAC
    Managed Identities
    Security Groups
    Privileged Identity Management (PIM)
    Hybrid identity where required

Basic flow:

    User / Service Principal / Managed Identity
                    ↓
             Microsoft Entra ID
                    ↓
                 RBAC
                    ↓
            Azure Resource

Landing Zone principle:

    Platform Team
       ↓
    Creates ALZ
       ↓
    Configures access controls
       ↓
    Workload Team gets required permissions
       ↓
    Workload Team manages its own resources

This is called:
    SUBSCRIPTION DEMOCRATIZATION

Meaning:
    Application teams get autonomy over their workloads,
    but within platform-defined policy guardrails.

17. IMPORTANT RBAC DESIGN RULE
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

Application team:

    Subscription / Resource Group scope
            ↓
        RBAC roles

Platform team:

    May have broader scope where operationally required.

Azure Policy:

    Management Group scope
            ↓
        Governance

Key principle:

    Policy at higher scope
    RBAC at required lower scope

This prevents application teams from modifying the governance
policies that control their landing zone.

18. NETWORK TOPOLOGY
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

Two major reference networking patterns:

    1. Hub-and-Spoke
    2. Azure Virtual WAN

Choose based on:
    → Number of regions
    → Branches
    → Hybrid connectivity
    → Traffic patterns
    → Operational model
    → Scale

Landing Zone itself is NOT tied to only one networking model.

33. NETWORK SECURITY vs GOVERNANCE
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

Network topology answers:

    "How will networks connect?"

Security answers:

    "How will we protect the traffic and workloads?"

Governance answers:

    "What networking/security configuration is allowed?"

Example:

    Network:
        Hub-Spoke

    Security:
        Azure Firewall

    Governance:
        Azure Policy restricting public IPs

These are related but different design areas.

34. DESIGN AREAS — BEFORE BUILDING LANDING ZONE
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

DO NOT immediately start creating VNets/subscriptions.

First understand organizational requirements.

Key design areas include:

    A → Azure Billing + Microsoft Entra Tenant
    B → Identity + Access Management
    C → Resource Organization
    D → Governance
    E → Network Topology + Connectivity
    F → Security
    G → Management
    H → [Additional organizational/environment considerations]
    I → Platform Automation + DevOps

The exact architecture should be adapted to:
    → Business requirements
    → Security requirements
    → Compliance
    → Connectivity
    → Operations
    → Scale

Microsoft reference architecture = STARTING POINT,
NOT a mandatory architecture for every organization.

36. SINGLE vs MULTIPLE MICROSOFT ENTRA TENANTS
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

Most organizations:

    ONE Microsoft Entra Tenant
             ↓
    Multiple Management Groups
             ↓
    Multiple Subscriptions
             ↓
    Multiple Workloads

Why single tenant?
    → Easier collaboration
    → Central governance
    → Central identity
    → Easier management

Multiple tenants may be required due to:
    → Organizational separation
    → Regulatory requirements
    → Security isolation
    → Business requirements

IMPORTANT:
    A subscription is associated with ONE Microsoft Entra tenant.

37. REGIONS & LANDING ZONES
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

Landing Zone architecture is REGION-AGNOSTIC.

But actual resources are deployed into Azure regions.

Consider:

    Primary Region
    Secondary/DR Region
    Data residency
    Availability
    Latency
    Regulatory requirements

Example:

    Primary:
        East US

48. COMMON INTERVIEW TRAPS
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

TRAP 1:
    "Landing Zone means VNet."

CORRECT:
    Landing Zone is the complete enterprise foundation.

TRAP 2:
    "Hub-Spoke is Landing Zone."

CORRECT:
    Hub-Spoke is a networking topology.

TRAP 3:
    "Every environment gets a Management Group."

CORRECT:
    Don't normally create MGs for DEV/TEST/PROD.
    Use subscriptions within workload-type MGs.

TRAP 4:
    "Every workload needs multiple subscriptions."

CORRECT:
    Multiple subscriptions only when requirements justify them.

TRAP 5:
    "Platform team manages all application resources."

CORRECT:
    Platform provides foundation/guardrails;
    workload team operates workload resources.

TRAP 6:
    "Policy controls users."

CORRECT:
    RBAC controls access.
    Policy controls resource configuration/compliance.

TRAP 7:
    "Identity subscription contains Microsoft Entra ID."

CORRECT:
    Microsoft Entra ID is tenant-level identity.
    Identity subscription contains supporting identity infrastructure.

TRAP 8:
    "Create Management Groups based on every Azure region."

CORRECT:
    Don't create regional MGs unless regulatory/business requirements require it.

49. MOST IMPORTANT DESIGN PRINCIPLES
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

1. SUBSCRIPTION DEMOCRATIZATION
   → Workload teams manage their own workloads within guardrails.

2. POLICY-DRIVEN GOVERNANCE
   → Use Azure Policy to enforce governance consistently.

3. SINGLE CONTROL & MANAGEMENT PLANE
   → Prefer consistent Azure-native management/control across the estate.

4. APPLICATION-CENTRIC SERVICE MODEL
   → Organize around workloads rather than infrastructure alone.

5. AZURE-NATIVE ALIGNMENT
   → Prefer Azure-native capabilities and align with Azure roadmap.

6. CENTRALIZE ONLY WHEN JUSTIFIED
   → Centralize where governance, operational or economic benefits exist.

7. AUTOMATE AT SCALE
   → Use IaC + CI/CD + subscription vending.

8. KEEP MANAGEMENT GROUPS SIMPLE
   → Avoid unnecessary nesting.

53. "HOW WOULD YOU DESIGN AN AZURE LANDING ZONE?"
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

INTERVIEW ANSWER:

"I would first understand the organization's requirements around identity,
networking, security, governance, resource organization and operations.

I would then establish the Management Group hierarchy and build the Platform
Landing Zone for centralized capabilities such as connectivity, identity,
security and management.

Under the Landing Zones management group, I would create Application Landing
Zones for workloads and classify them according to their requirements, such as
Corp, Online or Local.

For networking, I would select Hub-Spoke or Azure Virtual WAN based on the
organization's scale, connectivity and traffic requirements.

Azure Policy would provide governance and RBAC would control access. Centralized
monitoring and security would be implemented using services such as Azure
Monitor, Log Analytics, Defender for Cloud and Microsoft Sentinel.

Finally, I would automate the platform and Application Landing Zone provisioning
using Infrastructure as Code and CI/CD, including a subscription vending process
for repeatable onboarding."

58. GOLDEN INTERVIEW ANSWER
────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

"Azure Landing Zone is a standardized enterprise foundation for governing,
securing and scaling Azure workloads across multiple subscriptions.

It has two major components: the Platform Landing Zone and Application Landing
Zones. The Platform Landing Zone provides centralized capabilities such as
Management Groups, governance, identity, connectivity, security and management.
Application Landing Zones are the environments where workload teams deploy and
operate their applications.

I would use Management Groups and Azure Policy for governance, Microsoft Entra
ID and RBAC for identity and access, Hub-Spoke or Azure Virtual WAN for
connectivity, and Azure Monitor, Defender for Cloud and Sentinel for operations
and security.

I would also implement subscription vending and Infrastructure as Code using
Terraform with CI/CD so that new landing zones can be provisioned consistently
and repeatedly.

The key principle is to give workload teams autonomy while enforcing enterprise
security and governance through centralized platform guardrails."
