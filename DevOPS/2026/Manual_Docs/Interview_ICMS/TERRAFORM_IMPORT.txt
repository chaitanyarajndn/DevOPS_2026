                    TERRAFORM IMPORT — BASIC TO ENTERPRISE PRACTICE
                    Azure Infrastructure Engineer | Interview + Real-World Implementation
================================================================================================================

1. WHAT IS TERRAFORM IMPORT?
----------------------------------------------------------------------------------------------------------------
Terraform Import is used to bring an EXISTING Azure resource under Terraform management without creating it again.

Example: Azure Portal se company ne RG, VNet, Subnets aur NSGs create kiye. Ab company chahti hai ki in resources
ko Terraform se manage kiya jaye. Hum existing resources ko import karenge instead of recreating them.

BEFORE IMPORT:                               AFTER IMPORT:
Azure Resource  -> Exists                    Azure Resource   -> Exists
Terraform Code  -> Not available/mapped      Terraform Code   -> Defines desired configuration
Terraform State -> Does not track resource   Terraform State  -> Tracks resource

IMPORTANT:
- Traditional `terraform import` command existing resource ko Terraform state ke saath associate karta hai.
- Ye command automatically complete .tf configuration generate nahi karta.
- Import ke baad configuration aur actual Azure resource mein differences ho sakte hain.
- Isliye import successful hone ke baad Terraform Plan review karna mandatory practice hai.

INTERVIEW ANSWER:
"Terraform Import is used to bring existing infrastructure under Terraform management. For example, if a VNet was
created manually in Azure, I can import it into Terraform state, maintain the corresponding resource configuration
and validate it using Terraform Plan before allowing any infrastructure changes."

2. THE 3 BASIC STEPS OF TERRAFORM IMPORT
----------------------------------------------------------------------------------------------------------------
STEP 1: WRITE TERRAFORM CONFIGURATION
Suppose Azure mein ye Resource Group already exists:
    Name = rg-icms-dev | Region = Central India

Create main.tf:
    resource "azurerm_resource_group" "icms" {
      name     = "rg-icms-dev"
      location = "Central India"
    }

Explanation: `azurerm_resource_group.icms` is the Terraform resource address where this existing resource will be
managed. Configuration resource type, name and relevant arguments define karte hain.

STEP 2: IMPORT THE EXISTING RESOURCE
Initialize Terraform:
    terraform init

Import command:
    terraform import azurerm_resource_group.icms "/subscriptions/<SUBSCRIPTION_ID>/resourceGroups/rg-icms-dev"

Command breakdown:
    azurerm_resource_group.icms = Terraform resource address
    /subscriptions/...          = Existing Azure Resource ID
    <SUBSCRIPTION_ID>            = Actual Azure subscription ID

STEP 3: VERIFY USING TERRAFORM PLAN
    terraform plan

Expected result, if configuration matches:
    No changes. Your infrastructure matches the configuration.

Agar Terraform update, deletion ya replacement propose karta hai, toh apply karne se pehle difference investigate karo.
IMPORTANT: Traditional CLI import command state update karta hai; import ke baad configuration ko manually maintain
karna padta hai. Resource block mein missing ya incorrect arguments unwanted changes propose kar sakte hain.

3. WHAT IF WE HAVE 100 OR 500 EXISTING AZURE RESOURCES?
----------------------------------------------------------------------------------------------------------------
Enterprise example: An existing subscription contains 20 Resource Groups, 15 VNets, 80 Subnets, 30 NSGs,
10 Virtual Machines, 15 Storage Accounts, 10 Key Vaults and other resources.

Total = 200+ resources.

Har resource ke liye manually command execute karna possible hai:
    terraform import <RESOURCE_ADDRESS> <AZURE_RESOURCE_ID>

Lekin large-scale onboarding mein challenges:
    1. Har resource ka correct Azure Resource ID identify karna.
    2. Har resource ke liye correct Terraform address aur configuration maintain karna.
    3. Resource dependencies aur nested-resource relationships samajhna.
    4. Duplicate imports aur incorrect state ownership avoid karna.
    5. Configuration ko existing infrastructure ke saath align karna.
    6. Generated code ko enterprise modules, naming standards aur governance ke according organize karna.

THERE ARE TWO IMPORTANT APPROACHES:
    A. Terraform Import Blocks -> Useful when you want configuration-driven, reviewable imports.
    B. Azure Export for Terraform (aztfexport) -> Useful when onboarding existing Azure resources at scale.

================================================================================================================
4. APPROACH A — TERRAFORM IMPORT BLOCKS
----------------------------------------------------------------------------------------------------------------
Import blocks Terraform configuration ke andar import mapping define karne ka method hain. Ye Terraform 1.5+ mein
introduce hue the. Traditional CLI import ke comparison mein ye imports ko normal plan/apply workflow mein laate hain.

Example: imports.tf
    import {
      to = azurerm_resource_group.icms
      id = "/subscriptions/<SUBSCRIPTION_ID>/resourceGroups/rg-icms-dev"
    }

    import {
      to = azurerm_virtual_network.icms
      id = "/subscriptions/<SUBSCRIPTION_ID>/resourceGroups/rg-icms-dev/providers/Microsoft.Network/virtualNetworks/vnet-icms-dev"
    }

Corresponding resource configuration bhi define honi chahiye:
    resource "azurerm_resource_group" "icms" {
      name     = "rg-icms-dev"
      location = "Central India"
    }

    resource "azurerm_virtual_network" "icms" {
      name                = "vnet-icms-dev"
      location            = azurerm_resource_group.icms.location
      resource_group_name = azurerm_resource_group.icms.name
      address_space       = ["10.10.0.0/16"]
      # Add the required subnet configuration.
    }

WORKFLOW:
    1. Resource configuration + import blocks define karo.
    2. terraform init
    3. terraform plan -> Import actions aur proposed infrastructure changes review karo.
    4. terraform apply -> Approved plan execute karo.
    5. terraform plan -> Verify karo ki configuration aur state aligned hain.

WHY ENTERPRISE TEAMS MAY PREFER IMPORT BLOCKS:
    - Import mapping code review aur version control mein rehti hai.
    - Multiple resources ek reviewed workflow mein import ho sakte hain.
    - CI/CD workflow mein imports ko controlled approval process se execute kar sakte hain.
    - Import mapping ko code se maintain karna traditional manual command execution se easier ho sakta hai.

IMPORTANT: Import blocks resources ki complete configuration automatically generate nahi karte. Resource definitions
tumhe maintain karni hoti hain. Agar desired configuration existing Azure resource se differ karti hai, toh plan
import ke saath update ya replacement bhi propose kar sakta hai. Isliye plan carefully review karo.

5. APPROACH B — WHAT IS AZTFEXPORT?
----------------------------------------------------------------------------------------------------------------
aztfexport = Azure Export for Terraform.

Ye Microsoft ka command-line tool hai jo existing Azure infrastructure ko Terraform management ke under lane mein
help karta hai. Ye supported resources ke liye Terraform configuration aur state export karne mein help karta hai.

WHY IS IT USEFUL?
Suppose enterprise ke Azure subscription mein 150 existing resources hain. Har resource ko manually discover karna,
uska import ID find karna aur initial Terraform configuration likhna time-consuming ho sakta hai.

aztfexport discovery/export process automate karne mein help karta hai. Lekin generated configuration ko review aur
standardize karna phir bhi zaroori hai.

EXPORT SCOPE:
    1. Individual resource.
    2. Resource Group aur uske resources.
    3. Azure Resource Graph query ke through selected resources.

Tool AzureRM (Azure Resource Manager) provider ko default provider ke roop mein support karta hai; AzAPI provider
ke through export ka option bhi available hai. Actual supported resources aur export behavior tool documentation
aur version par depend karte hain.

6. AZTFEXPORT — PRACTICAL IMPLEMENTATION
----------------------------------------------------------------------------------------------------------------
PREREQUISITES:
    - Azure CLI installed and authenticated.
    - Required Azure subscription/resource access.
    - Terraform CLI installed.
    - AzureRM provider compatibility checked.
    - Dedicated working directory created.
    - Target state aur existing Terraform ownership understood.

STEP 1: SIGN IN TO AZURE
    az login

STEP 2: SELECT THE CORRECT SUBSCRIPTION
    az account set --subscription "<SUBSCRIPTION_ID>"

Verify:
    az account show

STEP 3: CREATE A DEDICATED EXPORT DIRECTORY
    mkdir C:\Terraform-Import\ICMS-Dev
    cd C:\Terraform-Import\ICMS-Dev

Why separate directory? Generated files ko review karne aur existing production Terraform repository/state ko
accidentally overwrite ya mix hone se bachane ke liye.

STEP 4: EXPORT AN EXISTING RESOURCE GROUP
    aztfexport resource-group rg-icms-dev

Tool selected scope ke supported resources ko export karne mein help karta hai. Interactive workflow mein resource
mappings review kar sakte ho. Export mode ke according generated configuration aur state artifacts inspect karo.

STEP 5: REVIEW GENERATED FILES
    - Generated .tf files aur resource arguments check karo.
    - Resource IDs, names, regions, tags aur dependencies verify karo.
    - Unsupported ya skipped resources identify karo.
    - Sensitive values aur configuration mein exposed secrets check karo.
    - Confirm karo ki generated state expected resources ko represent karta hai.

STEP 6: VALIDATE GENERATED CONFIGURATION
    terraform init
    terraform validate
    terraform plan

EXPECTED RESULT:
    No changes needed.

Iska matlab current configuration aur state, Terraform dwara evaluate kiye jaane wale attributes ke liye, actual
infrastructure ke saath aligned hain. Agar plan changes propose kare, toh reason identify karo; production mein
blindly apply mat karo.

IMPORTANT:
    aztfexport se generated configuration ko production-ready assume mat karo. Resource support, provider behavior,
    dependencies aur export scope ke hisaab se manual corrections required ho sakti hain.

7. TERRAFORM IMPORT vs IMPORT BLOCKS vs AZTFEXPORT
----------------------------------------------------------------------------------------------------------------
+----------------------+---------------------------+-----------------------------+------------------------------+
| Feature              | terraform import CLI      | Import blocks               | aztfexport                   |
+----------------------+---------------------------+-----------------------------+------------------------------+
| Main purpose         | Import into state         | Configuration-based import  | Export existing Azure infra  |
| Resource exists?     | Yes                       | Yes                         | Yes                          |
| Generates .tf code?  | No                        | No                          | Yes, for supported resources |
| Updates/exports state| Updates target state       | Updates state via apply      | Exports state information    |
| Multiple resources   | Usually repeated commands | Multiple import blocks      | Resource/group/query scopes  |
| Best fit             | Few resources             | Reviewed import workflows   | Large-scale onboarding       |
+----------------------+---------------------------+-----------------------------+------------------------------+

PRACTICAL SELECTION:
    Few resources + existing Terraform configuration -> terraform import / import blocks.
    Many existing resources + little/no initial configuration -> Evaluate aztfexport.
    Existing modular Terraform repository -> Export for discovery, then map resources carefully to module addresses.

IMPORTANT: aztfexport is not a replacement for code review, module design, state migration planning or Terraform Plan.

8. ENTERPRISE PRACTICE — ICMS EXISTING INFRASTRUCTURE
----------------------------------------------------------------------------------------------------------------
SCENARIO:
ICMS application Azure par already running hai. Kuch resources manually create hue the, aur company unhe Terraform
se manage karna chahti hai.

Existing resources:
    Resource Group -> VNet -> Subnets -> NSGs -> AKS -> ACR -> Key Vault.

PHASE 1 — DISCOVERY:
    Azure resource inventory banao; subscription, resource IDs, owners, dependencies aur existing state identify karo.
    Confirm karo kaunse resources Terraform manage karega aur kaunse intentionally external rahenge.

PHASE 2 — EXPORT / IMPORT:
    Suitable scope ke liye aztfexport evaluate karo. Agar existing configuration available hai, toh import blocks ya
    traditional import use kar sakte ho. Correct target state aur resource addresses pehle determine karo.

PHASE 3 — CODE STANDARDIZATION:
    Generated code ko approved repository structure, reusable modules, naming conventions, variables, tags aur
    environment-specific configurations ke saath align karo. Generated files ko blindly production repository mein
    copy mat karo.

PHASE 4 — STATE MANAGEMENT:
    Correct remote backend/state boundary confirm karo. State backup aur locking procedure verify karo. Ensure karo
    ki same Azure resource multiple Terraform state addresses se manage nahi ho raha.

PHASE 5 — PLAN VALIDATION:
    Terraform Plan mein unexpected updates, deletions aur replacements identify karo. Differences resolve karo.
    Production resources ke liye destructive plan ko approval ke bina execute mat karo.

PHASE 6 — APPROVAL + HANDOVER:
    Peer review aur required approvals lo. Approved import execute karo. Fresh plan run karo aur confirm karo ki
    future Terraform changes intended configuration ke according hain.

ENTERPRISE FLOW:
    Resource Inventory -> Export/Import -> Code Standardization -> State Verification -> Plan Review
                    -> Approval -> Terraform Management through CI/CD

9. AZTFEXPORT + EXISTING MODULAR TERRAFORM REPOSITORY
----------------------------------------------------------------------------------------------------------------
Suppose repository structure:
    azure-terraform-modular/
    |-- modules/
    |   |-- resource_group/
    |   |-- virtual_network/
    |   |-- subnet/
    |   `-- network_security_group/
    `-- environment/
        `-- dev/
            |-- main.tf
            |-- variables.tf
            `-- terraform.tfvars

Azure mein existing VNet hai. Tum aztfexport se uski initial configuration generate karte ho.

KYA GENERATED FILES DIRECTLY environment/dev MEIN COPY KARNE CHAHIYE?
Not necessarily. Agar repository modules use karti hai, toh existing resource ko correct module resource address se
associate karna chahiye. Exported resource configuration ko module inputs aur resource definitions ke according
reconcile karna padega.

Example module resource address:
    module.virtual_network.azurerm_virtual_network.this

Import block:
    import {
      to = module.virtual_network.azurerm_virtual_network.this
      id = "/subscriptions/<SUBSCRIPTION_ID>/resourceGroups/rg-icms-dev/providers/Microsoft.Network/virtualNetworks/vnet-icms-dev"
    }

IMPORTANT:
    Ye address tabhi valid hai jab module ke andar actual resource address yahi ho. Module configuration aur required
    inputs correct hone chahiye. Resource ko intended state mein import karo; exported temporary state ko sirf .tf
    files copy karke doosre backend mein automatically transfer nahi kiya ja sakta.

10. WHAT IF THE RESOURCE IS ALREADY IN TERRAFORM STATE?
----------------------------------------------------------------------------------------------------------------
Check state:
    terraform state list

Inspect a resource:
    terraform state show azurerm_virtual_network.icms

If resource is already in the intended state:
    Duplicate import mat karo.

If resource exists in Azure but not in the intended state:
    Resource ID, current state ownership aur target address verify karo.

If another Terraform state already manages it:
    Pehle controlled state migration/ownership transfer plan banao. Resource ko casually ek state se remove karke
    doosre state mein import mat karo; isse temporary ownership gap ya conflicting management ho sakta hai.

GOLDEN RULE:
    One Azure resource should have one intended Terraform state address for normal management. Import is not a
    substitute for a planned state migration.

11. INTERVIEW QUESTIONS — QUICK REVISION
----------------------------------------------------------------------------------------------------------------
Q1. Can Terraform Import create a resource?
A: No. It associates an existing resource with a Terraform state address.

Q2. Does traditional terraform import generate .tf files?
A: No. It updates state. aztfexport can generate Terraform configuration for supported Azure resources.

Q3. How would you import 200 Azure resources?
A: I would inventory the resources, check dependencies and state boundaries, evaluate aztfexport for bulk onboarding,
   review the generated configuration, align it with our modules and validate the plan before production approval.

Q4. Why can Terraform propose replacement after import?
A: Configuration differences, immutable attribute changes or resource/provider-specific behavior can cause a
   replacement proposal. I investigate the plan before applying any changes.

Q5. Can I import a VNet without importing its subnets?
A: It depends on how the subnets are represented. Some configurations manage subnets as nested VNet arguments,
   while others use separate subnet resources. I check the AzureRM provider resource model and current state before
   importing to avoid duplicate management.

Q6. What is the biggest risk during import?
A: Incorrect resource mapping, duplicate state ownership, configuration drift and unexpected infrastructure changes.
   I control these risks through discovery, state verification, code review and plan validation.

Q7. What happens if the import succeeds but Terraform Plan shows changes?
A: Import only establishes state association. I compare the actual resource, state and configuration, correct the
   intended configuration, then rerun Plan. I do not blindly apply unexpected changes.

12. FINAL REVISION — REMEMBER THIS
----------------------------------------------------------------------------------------------------------------
1. terraform import CLI -> Existing resource into Terraform state; does not generate .tf configuration.
2. Import blocks         -> Version-controlled, configuration-driven imports; resource configuration still required.
3. aztfexport            -> Helps export supported existing Azure resources into Terraform configuration/state.
4. Enterprise workflow   -> Discover -> Export/Import -> Standardize -> Verify State -> Review Plan -> Approve.
5. Production safety     -> Import success does not mean configuration is production-ready. Review every proposed
                            change before applying.
