AZURE GOVERNANCE — BASIC UNDERSTANDING
════════════════════════════════════════════════════════════════════════════════════════
1. WHAT IS AZURE GOVERNANCE?
   → Azure Governance = Rules + Controls + Standards used to manage Azure resources
     consistently across an organization.
   → It controls:
      → WHO can access resources
      → WHAT resources/configurations are allowed
      → WHERE resources can be deployed
      → HOW resources should be configured
      → HOW cost and compliance should be managed
   → Main goal:
      → Secure Azure environment
      → Consistent configuration
      → Controlled access
      → Cost control
      → Compliance
      → Standardized resource deployment
────────────────────────────────────────────────────────────────────────────────────────
2. SIMPLE ENTERPRISE EXAMPLE
   Company has:
      Tenant
       ↓
      Landing Zones Management Group
       ├── Prod Subscription
       ├── Dev Subscription
       └── Lab Subscription
   Organization defines:
      → Prod resources only in approved regions
      → Mandatory Environment/Owner/CostCenter tags
      → Public IP restricted
      → Encryption required
      → Access must follow RBAC standards
      → Production privileged access should use PIM
      → Budget and cost alerts required
   → Defining + applying + monitoring these rules = GOVERNANCE
────────────────────────────────────────────────────────────────────────────────────────
3. MAIN AREAS OF AZURE GOVERNANCE
   AZURE GOVERNANCE
   │
   ├── Management Groups
   │    → Organize subscriptions into hierarchy
   │
   ├── Azure Policy
   │    → Define/enforce resource rules
   │
   ├── Initiatives
   │    → Group multiple policies
   │
   ├── Resource Locks
   │    → Protect resources from accidental changes/deletion
   │
   ├── Tagging
   │    → Standardize resource identification and cost tracking
   │
   ├── Region Governance
   │    → Control approved Azure regions
   │
   ├── Resource Type Governance
   │    → Restrict unwanted resource types/services
   │
   ├── Network Governance
   │    → Enforce approved network patterns and restrictions
   │
   ├── Security Governance
   │    → Enforce security standards and configurations
   │
   ├── Cost Governance
   │    → Budgets, alerts and cost monitoring
   │
   └── Compliance
        → Ensure organizational/regulatory requirements are followed
────────────────────────────────────────────────────────────────────────────────────────
4. WHERE DO RBAC AND PIM FIT?
   → RBAC and PIM are primarily Identity & Access Management topics.
   → They are NOT exclusively Governance features.
   → Governance uses them as part of ACCESS GOVERNANCE.
   RBAC:
      → WHO can access?
      → WHAT can they do?
      → At WHICH scope?
   PIM:
      → WHO gets privileged access?
      → WHEN can they get it?
      → FOR HOW LONG?
   Example:
      Developer → Reader → Prod Subscription
      DevOps    → Contributor → Prod Subscription
      Admin     → Privileged access through PIM
   → Identity & Access = primary area
   → Governance = organizational control/standard around that access
────────────────────────────────────────────────────────────────────────────────────────
5. IMPORTANT INTERVIEW DISTINCTION
   Management Groups
      → Organize subscriptions + provide governance scope
   Azure Policy
      → WHAT is allowed/configured?
   Azure RBAC
      → WHO can do WHAT?
   PIM
      → HOW and WHEN privileged access is activated?
   Resource Locks
      → Can the resource be deleted/changed?
   Cost Management
      → HOW MUCH are we spending?
────────────────────────────────────────────────────────────────────────────────────────
6. ONE-LINE INTERVIEW ANSWER
   Q: What is Azure Governance?
   A: Azure Governance is the set of rules, controls and standards used to manage
      Azure resources consistently, securely and within organizational requirements.

1. MANAGEMENT GROUPS
════════════════════════════════════════════════════════════════════════════════════════
WHAT?
   → Container/hierarchy for subscriptions.
   → Used mainly to organize subscriptions and apply governance at scale.

WHERE?
   Azure Portal
      → Search "Management Groups"
      → Management Groups

SCOPE:
   → Above Subscription
   → Can contain other Management Groups
   → Contains Subscriptions

EXAMPLE:
   Tenant Root
      ↓
   Landing Zones MG
      ├── Prod Subscription
      ├── Dev Subscription
      └── Lab Subscription

PRACTICAL USE:
   → Put common policies at MG level.
   → Example: all Prod/Dev/Lab subscriptions must follow approved regions.

INTERVIEW:
   Q: Why Management Groups?
   A: To organize subscriptions and apply governance consistently across multiple
      subscriptions.

IMPORTANT:
   → Management Group is NOT a Resource Group.
   → It does NOT contain VMs, VNets, AKS etc.
   → It contains subscriptions and child management groups.

2. AZURE POLICY
════════════════════════════════════════════════════════════════════════════════════════
WHAT?
   → Azure Policy checks whether Azure resources follow organizational rules.
   → It can audit, deny, modify or deploy required configurations depending on
     the policy effect.

WHERE?
   Azure Portal
      → Search "Policy"
      → Policy

MAIN AREAS:
   Policy
      ├── Overview
      ├── Assignments
      ├── Definitions
      ├── Compliance
      └── Exemptions

SCOPE:
   Policy assignment can target:
      → Management Group
      → Subscription
      → Resource Group
      → Individual Resource

INHERITANCE:
   MG Policy
      ↓
   Subscription
      ↓
   Resource Group
      ↓
   Resources

   Subscription Policy
      ↓
   Resource Groups
      ↓
   Resources

   Resource Group Policy
      ↓
   Resources inside that RG

Microsoft confirms that policy assignments can range from Management Group
down to an individual resource, with child resources inheriting assignments. :contentReference[oaicite:2]{index=2}

3. POLICY DEFINITION
════════════════════════════════════════════════════════════════════════════════════════
WHAT?
   → Defines the actual RULE.

Example:
   "Allowed locations should be Central India and East US."

OR:
   "Resources must have an Environment tag."

WHERE?
   Azure Portal
      → Policy
      → Definitions

DEFINITION LOCATION:
   → Management Group
   → Subscription

IMPORTANT:
   Definition ≠ Assignment

   Definition:
      → What is the rule?

   Assignment:
      → Where do I apply the rule?

Example:
   Definition:
      "Allowed locations = specified locations"

   Assignment:
      → Prod Subscription

Microsoft currently allows a policy definition to be created at either
subscription or management-group definition location. :contentReference[oaicite:3]{index=3}

4. POLICY ASSIGNMENT
════════════════════════════════════════════════════════════════════════════════════════
WHAT?
   → Applies a Policy Definition to a particular scope.

WHERE?
   Azure Portal
      → Policy
      → Assignments
      → Assign Policy

SCOPE OPTIONS:
   → Management Group
   → Subscription
   → Resource Group
   → Resource

Example:
   Policy Definition:
      "Allowed Locations"

   Assignment:
      Scope = Landing Zones MG

   Result:
      Prod + Dev + Lab subscriptions can inherit the policy.

OR:

   Scope = Prod Subscription

   Result:
      Policy applies to Prod and its child resources.

PORTAL FLOW:
   Policy
      ↓
   Assignments
      ↓
   Assign Policy
      ↓
   Scope
      ↓
   Policy Definition
      ↓
   Parameters
      ↓
   Review + Create

The current portal assignment flow explicitly lets you select subscription/resource

5. POLICY PARAMETERS
════════════════════════════════════════════════════════════════════════════════════════
WHAT?
   → Parameters make the same Policy Definition reusable with different values.

Example Policy Definition:
   "Allowed locations"

Assignment 1:
   Prod
      → Central India
      → East US

Assignment 2:
   Dev
      → Central India
      → West Europe

Instead of creating two policies:
   ❌ Allowed Locations - Prod
   ❌ Allowed Locations - Dev

Create one parameterized policy:
   ✅ Allowed Locations

Then provide different parameter values during assignment.

WHERE?
   → Inside Policy Assignment configuration.

FLOW:
   Policy Definition
       ↓
   Parameters
       ↓
   Policy Assignment
       ↓
   Parameter Value

INTERVIEW:
   Q: Why use parameters?
   A: To reuse the same policy definition for different environments or scopes
      without creating separate policies.

6. POLICY EFFECTS
════════════════════════════════════════════════════════════════════════════════════════
WHAT?
   → Effect defines WHAT happens when a resource violates the policy.

COMMON EFFECTS:
   Audit
      → Resource is allowed but marked non-compliant.

   Deny
      → Deployment/update is blocked.

   Modify
      → Azure Policy can modify/add properties during deployment/update.
      → Common example: tags.

   Append
      → Adds a value/property to the request/resource where supported.

   DeployIfNotExists
      → If required resource/configuration doesn't exist,
        deploy the required configuration through remediation.

   Disabled
      → Policy is effectively disabled.

PRACTICAL EXAMPLE:

   Policy:
      "Resources must have Environment tag"

   Effect = Audit
      → Resource gets created
      → Compliance = Non-compliant

   Effect = Deny
      → Resource without required tag
      → Deployment blocked

   Effect = Modify
      → Policy can add/modify the tag where the policy is designed to do so.

Microsoft provides built-in tagging policies using effects such as
deny, append and modify, including remediation for existing resources. :contentReference[oaicite:5]{index=5}

7. INITIATIVE / POLICY SET
════════════════════════════════════════════════════════════════════════════════════════

Example:
   "Production Security Baseline"
      │
      ├── Allowed Locations
      ├── Require HTTPS
      ├── Require Encryption
      ├── Audit Diagnostic Settings
      └── Required Tags

Instead of assigning:
   Policy 1
   Policy 2
   Policy 3
   Policy 4
   Policy 5

You assign:
   ONE Initiative
      ↓
   Multiple Policies

WHERE?
   Azure Portal
      → Policy
      → Definitions
      → Definition type = Initiative

ASSIGNMENT:
   Initiative can then be assigned at:
      → Management Group
      → Subscription
      → Resource Group
      → Resource

BEST ENTERPRISE USE:
   → Common security/compliance baseline at Management Group level.

8. POLICY EXEMPTIONS
════════════════════════════════════════════════════════════════════════════════════════
WHAT?
   → Allows a specific scope/resource to be excluded from a Policy assignment.

Example:

   Corp rule:
      "Public IP is not allowed."

   ↓

   Prod Subscription
      ↓
   ICMS Resource Group
      ↓
   One approved application requires Public IP

Instead of removing the entire policy:

   ❌ Remove policy

Use:

   Policy Exemption
      ↓
   Specific approved scope

WHERE?
   Azure Portal
      → Policy
      → Exemptions

IMPORTANT:
   → Exemption should be controlled/documented.
   → Don't use exemptions simply to bypass governance.

POLICY:
   Applied at MG
       ↓
   Prod Subscription
       ↓
   Exclude approved RG/resource through exemption

9. RESOURCE LOCKS
════════════════════════════════════════════════════════════════════════════════════════
WHAT?
   → Protect Azure resources from accidental deletion or modification.

TYPES:

   CanNotDelete
      → Resource can be modified
      → Resource cannot be deleted

   ReadOnly
      → Resource cannot be modified/deleted through normal management operations.

WHERE?
   Azure Portal
      → Resource / Resource Group / Subscription
      → Locks
      → Add

SCOPE:
   → Subscription
   → Resource Group
   → Resource

EXAMPLE:

   Prod
      ↓
   Critical Key Vault
      ↓
   CanNotDelete

   Someone tries to delete it
      ↓
   Delete operation blocked by lock.

IMPORTANT:
   → Lock is different from Azure Policy.
   → Policy controls compliance/deployment rules.
   → Lock protects against management operations such as deletion/change.

10. TAGGING GOVERNANCE
════════════════════════════════════════════════════════════════════════════════════════
WHAT?
   → Tags are key/value metadata attached to Azure resources.

Example:
   Environment = Prod
   Application = ICMS
   Owner = DevOps
   CostCenter = 1001

WHY?
   → Resource identification
   → Cost allocation
   → Ownership
   → Environment tracking
   → Automation/reporting

IMPORTANT:
   Tags themselves are NOT a hierarchy/scope like Management Groups.

WHERE CAN TAGS BE USED?
   → Resources
   → Resource Groups
   → Subscriptions also support tagging

HOW TO ENFORCE?
   Azure Policy

Example:
   Policy:
      "Environment tag is required"

   Scope:
      Landing Zones MG

   Result:
      Child subscriptions/resources are evaluated according to assignment.

PRACTICAL:
   Tags
      +
   Azure Policy
      ↓
   Tagging Governance

Microsoft specifically recommends Azure Policy for enforcing and automatically
applying tagging rules at scale. :contentReference[oaicite:6]{index=6}

17. GOVERNANCE AT SCALE
════════════════════════════════════════════════════════════════════════════════════════
WHAT?
   → Applying common governance to many subscriptions without configuring every
     subscription manually.

EXAMPLE:

   Tenant Root
       ↓
   Landing Zones MG
       │
       ├── Prod Subscription
       ├── Dev Subscription
       └── Lab Subscription

   Policy:
      Allowed Locations
      Required Tags
      Security Baseline

   Assigned at:
      Landing Zones MG

   ↓

   Child subscriptions inherit the assignment
   ↓
   Resources are evaluated

WHY?
   5 subscriptions:
      → Manual management may still be possible.

   50/100+ subscriptions:
      → Centralized governance becomes essential.

BEST PRACTICE:
   → Use Management Groups as governance boundaries.
   → Assign common Policies/Initiatives at appropriate MG levels.
   → Avoid unnecessary assignments at the root MG.
   → Use lower scopes where requirements differ.

Microsoft's current Landing Zone guidance recommends Management Groups for
policy/initiative governance across subscriptions and cautions against putting
application-team RBAC broadly at Management Group scope. :contentReference[oaicite:8]{index=8}

19. VERY IMPORTANT — SCOPE VS IDENTITY
════════════════════════════════════════════════════════════════════════════════════════
   Azure GOVERNANCE SCOPE:
      Management Group
           ↓
      Subscription
           ↓
      Resource Group
           ↓
      Resource

   IDENTITY:
      User
      Group
      Service Principal
      Managed Identity

   RBAC:
      Identity
         ↓
      Role
         ↓
      Scope

   Example:
      DevOps Group
          ↓
      Contributor
          ↓
      Prod Subscription

   Managed Identity is NOT a governance scope.
   It is an identity/security principal that can receive permissions through RBAC.
