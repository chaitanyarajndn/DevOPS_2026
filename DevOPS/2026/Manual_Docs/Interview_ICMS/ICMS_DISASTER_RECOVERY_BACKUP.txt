| East US            | Virginia             | Yes: 1,2,3         | West US              |
| East US 2          | Virginia             | Yes: 1,2,3         | Central US            |
| Central US         | Iowa                 | Yes: 1,2,3         | East US 2             |

| West US 3          | Phoenix              | Yes: 1,2,3         | East US               |

Microsoft's current region list identifies the physical location, Availability Zone
support and pairing for these regions. :contentReference[oaicite:1]{index=1}

IMPORTANT:
"Availability Zone 1/2/3" does NOT mean you can identify them as:
    Zone 1 = Building A
    Zone 2 = Building B
    Zone 3 = Building C

Microsoft deliberately abstracts the physical datacenter mapping. Availability
Zones are physically separate locations within the region, with independent
power, cooling and networking. :contentReference[oaicite:2]{index=2}


2. WHICH US REGION WOULD I CHOOSE FOR ICMS?
══════════════════════════════════════════════════════════════════════════════

There is no universal answer such as:

    "East US is always the primary region."

I would select the region based on:

    Business user location
    Application latency
    Azure service availability
    VM SKU availability
    AKS availability
    Database capabilities
    Compliance/data residency
    Network connectivity
    Azure quota/capacity
    Cost
    DR requirements

For a US enterprise ICMS example, I can assume:

    PRIMARY REGION
        East US

    DR REGION
        West US 3

Why?

    East US
       |
       +-- Mature Azure region
       +-- Availability Zones
       +-- Strong service availability

    West US 3
       |
       +-- Separate geographic location
       +-- Availability Zones
       +-- Independent regional failure domain

Microsoft lists West US 3 as paired with East US. :contentReference[oaicite:3]{index=3}

But there is an important enterprise point:

    Region Pair != mandatory DR region

Azure SQL Database failover groups can be configured across Azure regions and
do not require the regions to be an official Azure region pair. Therefore the
final choice should be based on workload requirements rather than blindly
choosing the paired region. :contentReference[oaicite:4]{index=4}


3. REGION VS AVAILABILITY ZONE
══════════════════════════════════════════════════════════════════════════════

Think of the hierarchy like this:

    Azure Geography
          |
          +--------------------------------+
          |                                |
      East US                         West US 3
      REGION                           REGION
          |                                |
      +---+---+                        +---+---+
      |   |   |                        |   |   |
     AZ1 AZ2 AZ3                      AZ1 AZ2 AZ3
      |   |   |                        |   |   |
    DCs DCs DCs                      DCs DCs DCs


AVAILABILITY ZONE:

    Protects against:
        Rack failure
        Datacenter failure
        Power failure
        Cooling failure
        Local networking failure
        Zone-level failure

REGION:

    Protects against:
        Large-scale regional outage
        Regional service disruption
        Major geographic failure

Therefore:

    AZ = Regional HA
    Region = Regional DR


4. ICMS TARGET ARCHITECTURE
══════════════════════════════════════════════════════════════════════════════

I would use:

    PRIMARY:
        East US

    DR:
        West US 3

    DR MODEL:
        Active-Passive / Warm Standby

Why Active-Passive?

    ICMS has a central database and enterprise application.

    If the application is primarily dependent on one active database,
    Active-Passive is generally simpler and cheaper than maintaining fully
    active application/data tiers in both regions.

Microsoft specifically notes that active-passive can be appropriate when the
application depends on resources such as a database that is active in only
one region. :contentReference[oaicite:5]{index=5}

It is NOT:

For infrastructure:

    AKS Backup

        +-- Geo-replication

For database:

    Azure SQL Database
        |
        +-- Failover Group / Geo-replication / Backup


13. AZURE CONTAINER REGISTRY (ACR) DR
══════════════════════════════════════════════════════════════════════════════

Primary:

    ACR Premium
        |
        +-- East US
        |
        +-- West US 3 replica


Application image:

    icms-api:v1.25
          |
          +----------------------+
          |                      |
       East US                West US 3
          |                      |
      Primary ACR             Replica
          |                      |
      Primary AKS               DR AKS


Why?

Suppose:

    East US is completely unavailable.

DR AKS starts:

    DR AKS
       |
       v
    Pull icms-api:v1.25
       |
       v
    West US 3 ACR replica

Without registry availability in DR, you can have:

    DR AKS = HEALTHY
    Application = CANNOT START

because the required image cannot be pulled.

ACR Premium geo-replication is therefore an important multi-region design
component.

17. IMPORTANT: SQL REPLICATION IS NOT THE SAME AS BACKUP
══════════════════════════════════════════════════════════════════════════════

SQL Failover Group:

    Protects against:
        Region outage
        Database/server failure

SQL Backup:

    Protects against:
        Accidental deletion
        Data corruption
        Bad application operation
        Point-in-time recovery

Therefore:

    SQL
     |
     +-- Backup
     |
     +-- Point-in-Time Restore
     |
     +-- Long-Term Retention
     |
     +-- Geo Secondary
     |
     +-- Failover Group

Use multiple layers.


18. SQL RPO CONSIDERATION
══════════════════════════════════════════════════════════════════════════════

Cross-region SQL replication is asynchronous.

Therefore:

    PRIMARY
       |
       | asynchronous replication
       v
    SECONDARY

There can be replication lag.

Example:

    Primary:
        Transaction T100
        Transaction T101
        Transaction T102

    Secondary:
        T100
        T101

If primary suddenly disappears:

    T102 may not yet exist on secondary.

Therefore I would monitor:

    replication_lag_sec

and compare it with the required Recovery Point Objective (RPO).

Microsoft explicitly recommends monitoring geo-replication lag when designing
for disaster recovery. :contentReference[oaicite:11]{index=11}

26. EXAMPLE RPO / RTO
══════════════════════════════════════════════════════════════════════════════

For interview purposes, assume business gives:

    RPO = 15 minutes
    RTO = 60 minutes

Meaning:

    RPO 15 min:
        Maximum acceptable data loss = 15 minutes

    RTO 60 min:
        ICMS should be operational within 60 minutes


Then design against those targets.

Do NOT say:

    "I decided RPO is 15 minutes."

Say:

    "Business defined the RPO/RTO and I designed the infrastructure
     and recovery mechanisms to meet those targets."

31. WHAT I WOULD SAY IN AN INTERVIEW
══════════════════════════════════════════════════════════════════════════════

"Since ICMS is a US-based enterprise application, I would design disaster
recovery at two levels. First, I would use Availability Zones within the
primary region to protect against datacenter and zone-level failures. For
example, I could use East US with AKS node pools distributed across
Availability Zones 1, 2 and 3."

"For a regional disaster, I would deploy a separate AKS cluster in a
secondary region such as West US 3. AKS is regional, so I would not try to
stretch a single AKS cluster across regions. Both environments would be
provisioned through Terraform so the DR infrastructure remains reproducible."

"For data protection, I would configure Azure SQL Database with a secondary
database and Failover Group, because the database is the most critical
stateful component. I would also retain Azure SQL backups for point-in-time
recovery. For Kubernetes workloads, I would use Azure Backup for AKS with a
Backup Vault configured for Geo-Redundant Storage (GRS) and Cross Region
Restore."

"I would use Azure Container Registry (ACR) geo-replication so that the DR
AKS cluster can pull the same production container images. I would also
duplicate the networking stack, Private Endpoints, Private DNS, Azure
Firewall, Application Gateway, Key Vault access and monitoring in the DR
region."

"Finally, I would create a documented DR runbook covering incident
declaration, infrastructure validation, database failover, application
deployment, traffic failover, smoke testing and failback. I would perform
regular DR drills and compare the actual Recovery Point Objective (RPO) and
Recovery Time Objective (RTO) against the business targets."
