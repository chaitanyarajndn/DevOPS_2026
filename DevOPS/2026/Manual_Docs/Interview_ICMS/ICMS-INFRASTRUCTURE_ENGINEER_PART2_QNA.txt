Q4. Can you explain the Azure architecture of your ICMS project?

At a high level, the environment follows an Azure Landing Zone approach with a Hub-and-Spoke network architecture.

The Hub VNet provides centralized connectivity and network security services such as Azure Firewall, VPN Gateway and Azure Bastion. DNS services and the required DNS resolution layer are also part of the centralized connectivity design.

The workload environments are deployed in separate Spoke VNets for Dev, QA and Production.

Each Spoke contains the workload components such as Application Gateway, AKS and Private Endpoint subnets. Application Gateway has its own dedicated subnet, AKS has its own subnet and Private Endpoints are placed in their required dedicated subnet.

The Hub VNet and each Spoke VNet are connected using VNet Peering.

VNet peering is at the VNet level. We do not peer individual subnets.

Q7. What is the purpose of Terraform Remote Backend?

Terraform Remote Backend is used to store Terraform state centrally instead of keeping the state only on an engineer's local machine.

In our environment, the state is maintained in an Azure Storage Account.

Terraform uses the state to track the resources it manages and to determine the difference between the desired configuration and the existing infrastructure.

Centralized state is important for team-based infrastructure management, controlled changes and maintaining a consistent Terraform state across environments.

Q8. What infrastructure security controls do you use?

Security is handled through multiple layers.

At the network level, we use NSGs, Azure Firewall, network segmentation and private connectivity. Private Endpoints are used for private access to supported Azure services, and Private DNS provides the required name resolution.

At the identity level, we use Microsoft Entra ID, RBAC and managed identities according to the approved access model.

Azure Key Vault is used for managing secrets and sensitive configuration.

Azure Policy is used for governance and compliance controls.

Microsoft Sentinel is part of the centralized security monitoring layer, and Azure DDoS Protection can be part of the enterprise network protection strategy for public-facing resources where required.

The important point is that infrastructure security is applied through multiple controls rather than relying on a single service.

Q9. Explain Azure Policy and how you use it.

Azure Policy is used to enforce and validate governance and compliance requirements on Azure resources.

A policy definition contains the rule or requirement. That policy can then be assigned at an appropriate scope such as a management group, subscription or resource group.

For example, an organization can restrict deployment to approved regions, require specific tags or audit certain security configurations.

Depending on the requirement, policy effects can include Audit, Deny, Modify or DeployIfNotExists.

In my role, I work with the approved organizational policies and ensure that the infrastructure we deploy follows those governance requirements.

Q11. What is the difference between Backup and Disaster Recovery?

Backup mainly focuses on protecting and restoring data.

For example, if data is accidentally deleted, corrupted or needs to be restored, backup provides the recovery point.

Disaster Recovery is broader. It is the capability to recover the complete application service and its supporting dependencies after a major failure such as a regional outage.

Backup answers:

"Can I restore the required data?"

Disaster Recovery answers:

"Can I restore the required service and its dependencies?"

So backup and DR are related, but they solve different recovery requirements.

Q13. Explain your source-code promotion and release promotion process.

There is an important distinction between source-code promotion and release promotion.

Source-code promotion happens through the Git workflow, where code moves through feature branches, Pull Requests and approved branches.

Release promotion is the movement of an approved build or release into the next environment.

Typical flow:

Feature Branch
      |

      |
      v
Develop
      |
      v

      |

      |

      |
      v
Production Deployment

The key distinction is:

PR Merge       = Source-Code Promotion
Deployment     = Release Promotion

This distinction is important because merging code does not by itself mean that the production release has happened.

I check IP addressing, NSG rules, route tables and UDR (User Defined Route) configuration, firewall rules, VNet peering, DNS resolution, Private Endpoint status and relevant Azure logs.

An important point in a Hub-and-Spoke architecture is that the Hub and Spoke VNets are peered.

The subnets are not separately peered.

If traffic has to pass through Azure Firewall, routing can be controlled using UDRs and the required routing configuration.

IMPORTANT ARCHITECTURE RULES TO REMEMBER
================================================================

Hub VNet <======== VNet Peering ========> Spoke VNet

This is VNet-to-VNet peering.

NOT:

AKS Subnet <======> Firewall Subnet

There is no subnet-to-subnet peering.

Hub VNet:
Azure Firewall
VPN Gateway
Azure Bastion
DNS / DNS resolution components

Spoke VNet:
Application Gateway
AKS
Private Endpoint Subnet
Other workload subnets as required

Centralized Management / Security:
Azure Monitor
Log Analytics
Microsoft Sentinel
Backup / DR services

Azure Policy:
Governance / Compliance layer

Azure DDoS Protection:
Enterprise network protection for applicable public-facing resources;
not a subnet inside the Hub.

Private Endpoint:
Private connectivity

Private DNS:
Private name resolution

VNet Peering:
VNet-level connectivity

UDR:
Controls the routing path, including sending traffic through Azure
Firewall where required.

Source-Code Promotion:
Feature Branch -> PR -> Approved Branch

Release Promotion:
DEV -> QA -> PROD through the approved release process
