============================================================
01. AZURE NETWORKING — CORE COMPONENTS
============================================================

01. AZURE VIRTUAL NETWORK (VNET)
Definition : Azure VNet is a private networking boundary in Azure where resources communicate using private IP addresses.
Why Needed : • Defines IP address space and network segmentation.
             • Provides the base network for Azure workloads.
Interview  : "VNet is basically the network foundation of my Azure environment."

02. SUBNET
Definition : A subnet is a logical network segment created inside a VNet.
Why Needed : • Separates workloads such as Web, App, DB and Management.
             • Allows different network security and routing controls.
Interview  : "VNet is the overall network, while subnets divide it into logical sections."

03. IP ADDRESS
Definition : An IP address provides network identity to a resource.
Why Needed : • Identifies the source and destination of network communication.
             • Can be private for internal communication or public for internet access.
Interview  : "IP addressing defines how an Azure resource is identified and reached."

04. PUBLIC IP
Definition : A Public IP is an internet-routable IP address assigned to or associated with an Azure resource.
Why Needed : • Allows internet-facing connectivity.
             • Commonly used with Application Gateway, Load Balancer, VPN Gateway and Bastion.
Interview  : "I use a Public IP when a resource needs an internet-reachable access path."

05. PRIVATE IP
Definition : A Private IP is an internal IP address used for communication within private networks.
Why Needed : • Enables internal resource-to-resource communication.
             • Avoids directly exposing resources to the internet.
Interview  : "Private IP keeps the communication within the private network path."

06. NETWORK INTERFACE (NIC)
Definition : A Network Interface Card is the networking interface through which an Azure VM connects to a VNet.
Why Needed : • Connects the VM to a subnet.
             • Holds network configuration such as private IP and NSG association.
Interview  : "NIC is basically the network connection point of an Azure VM."

07. NETWORK SECURITY GROUP (NSG)
Definition : NSG is a network traffic filtering mechanism that allows or denies inbound and outbound traffic.
Why Needed : • Controls which traffic can reach a resource.
             • Provides basic network-level access control.
Applied    : Subnet level / NIC level
Interview  : "NSG provides basic network-level traffic control by allowing or denying inbound and outbound traffic."

08. AZURE BASTION
Definition : Azure Bastion is a managed service that provides secure RDP/SSH access to VMs through Azure Portal.
Why Needed : • Allows administration without assigning a public IP directly to the VM.
             • Reduces direct internet exposure of management ports.
Interview  : "Bastion gives me secure RDP or SSH access to private VMs without exposing those VMs directly to the internet."

09. VNET PEERING
Definition : VNet Peering connects two Azure VNets using private network connectivity.
Why Needed : • Enables communication between resources in different VNets.
             • Commonly used in Hub-and-Spoke architecture.
Interview  : "VNet Peering allows separate VNets to communicate using private network connectivity."

10. AZURE LOAD BALANCER
Definition : Azure Load Balancer is a Layer 4 load-balancing service for TCP and UDP traffic.
Why Needed : • Distributes network traffic across backend instances.
             • Improves availability by sending traffic to healthy instances.
Interview  : "Azure Load Balancer distributes network-level traffic across healthy backend instances."

11. APPLICATION GATEWAY
Definition : Application Gateway is a Layer 7 web traffic load balancer for HTTP/HTTPS applications.
Why Needed : • Supports application-aware routing such as host-based and URL-based routing.
             • Can provide TLS termination and integrate with WAF.
Interview  : "Application Gateway understands web traffic, so I can route HTTP/HTTPS requests based on application-level rules."

12. NAT GATEWAY
Definition : NAT Gateway is a managed Network Address Translation service for outbound internet connectivity.
Why Needed : • Provides predictable outbound internet access for private resources.
             • VMs do not need individual public IPs for outbound connectivity.
Interview  : "NAT Gateway provides controlled and predictable outbound internet connectivity for resources in a subnet."

13. VPN GATEWAY
Definition : VPN Gateway provides encrypted connectivity between Azure and external networks over the internet.
Why Needed : • Connects Azure with on-premises environments.
             • Commonly used for Site-to-Site VPN connectivity.
Interview  : "VPN Gateway creates an encrypted tunnel between Azure and an external network over the internet."

14. EXPRESSROUTE
Definition : ExpressRoute provides private connectivity between on-premises infrastructure and Azure.
Why Needed : • Provides private and predictable network connectivity.
             • Useful for enterprise workloads requiring dedicated connectivity.
Interview  : "ExpressRoute provides private connectivity to Azure without using the public internet path."

15. GATEWAY TRANSIT
Definition : Gateway Transit allows a peered VNet to use the VPN or ExpressRoute gateway deployed in another VNet.
Why Needed : • Avoids deploying a separate gateway in every spoke.
             • Commonly used in Hub-and-Spoke architecture.
Interview  : "Gateway Transit allows spoke VNets to use the connectivity gateway deployed in the hub."

16. USER DEFINED ROUTE (UDR)
Definition : UDR is a custom route created to control the path network traffic takes.
Why Needed : • Forces traffic through a specific network appliance.
             • Commonly used to send traffic through Azure Firewall.
Interview  : "UDR allows me to define a custom traffic path instead of relying only on Azure's default routing."

17. AZURE FIREWALL
Definition : Azure Firewall is a managed, centralized network security service for controlling and inspecting network traffic.
Why Needed : • Provides centralized traffic control across network segments.
             • Can control and inspect north-south and east-west traffic.
Interview  : "Azure Firewall acts as a centralized security checkpoint for network traffic."

18. AZURE DNS
Definition : Azure DNS is Azure's DNS hosting service used to resolve domain names to IP addresses.
Why Needed : • Allows applications to be accessed using domain names.
             • Provides DNS management for Azure-hosted domains.
Interview  : "Azure DNS allows applications and users to reach resources using names instead of directly using IP addresses."

19. PRIVATE DNS ZONE
Definition : Private DNS Zone provides DNS name resolution inside private Azure networks.
Why Needed : • Resolves private endpoints and internal services.
             • Commonly used with Private Endpoint architecture.
Interview  : "Private DNS Zone allows private services to be resolved using DNS names inside the private network."

20. PUBLIC ENDPOINT
Definition : A Public Endpoint is an internet-reachable endpoint of an Azure service.
Why Needed : • Allows clients outside the private network to access a service.
             • Must be protected using appropriate security controls.
Interview  : "A public endpoint provides an internet-reachable access path to a service."

21. SERVICE ENDPOINT
Definition : Service Endpoint extends VNet/subnet identity to supported Azure PaaS services.
Why Needed : • Restricts service access based on virtual network rules.
             • Keeps traffic on the Azure backbone rather than requiring public internet routing.
Interview  : "Service Endpoint allows a subnet to access supported Azure services while restricting access at the virtual network level."

22. PRIVATE ENDPOINT
Definition : Private Endpoint provides a private IP address from the VNet for an Azure PaaS service.
Why Needed : • Provides private connectivity to services such as Key Vault and Storage.
             • Removes the need to rely on the service's public endpoint for access.
Interview  : "Private Endpoint gives an Azure service a private IP inside my VNet, allowing private connectivity to that service."

23. AZURE DDOS PROTECTION
Definition : Azure DDoS Protection helps protect internet-facing resources from Distributed Denial-of-Service attacks.
Why Needed : • Helps maintain application availability during abnormal traffic.
             • Provides protection for public-facing workloads.
Interview  : "DDoS Protection helps keep internet-facing applications available during large-scale malicious traffic attacks."

24. WEB APPLICATION FIREWALL (WAF)
Definition : WAF is a Layer 7 security capability that inspects HTTP/HTTPS traffic for malicious web requests.
Why Needed : • Protects web applications against common application-layer attacks.
             • Commonly deployed with Application Gateway.
Interview  : "WAF protects the web application by inspecting HTTP and HTTPS requests and blocking malicious traffic."

25. NETWORK WATCHER
Definition : Network Watcher is an Azure network monitoring and troubleshooting service.
Why Needed : • Helps identify connectivity and routing problems.
             • Provides tools such as IP Flow Verify and Connection Troubleshoot.
Interview  : "I use Network Watcher when I need to troubleshoot where network connectivity is failing."


============================================================
02. IMPORTANT AZURE NETWORK DIFFERENCES
============================================================

NSG              → L3/L4 traffic filtering → Subnet/NIC → Allow/Deny rules
Azure Firewall   → Centralized network security → Traffic inspection/control
Load Balancer    → L4 → TCP/UDP → Network traffic distribution
Application GW   → L7 → HTTP/HTTPS → Application-aware routing
WAF              → L7 security → Web attack protection
NAT Gateway      → Outbound connectivity → Private resources → Internet
VPN Gateway      → Encrypted connectivity → Internet-based VPN
ExpressRoute     → Private connectivity → Azure ↔ On-Premises
Bastion          → RDP/SSH management → Private VM → No VM public IP required
Service Endpoint → VNet identity → Supported Azure PaaS service
Private Endpoint → Private IP → PaaS service → Private connectivity

03. AZURE FIREWALL vs NSG
============================================================

NSG
Definition : Basic network traffic filtering at subnet/NIC level.
Why        : Controls which inbound/outbound traffic is allowed.
Use        : VM/subnet-level access control.

AZURE FIREWALL
Definition : Centralized managed network security service.
Why        : Centralizes traffic inspection and network security.
Use        : Hub-based security, outbound control, segmentation.

INTERVIEW:
"NSG is generally used for basic subnet or NIC-level filtering,
while Azure Firewall provides centralized network security and traffic inspection."

15. BACKUP
============================================================

Definition : Backup is the process of creating recoverable copies of data or workloads.
Why Needed : • Protects against accidental deletion, corruption or operational mistakes.
             • Provides a restore point when original data is unavailable.

Interview : "Backup gives me a recoverable copy of data so I can restore it after data loss or corruption."

16. DISASTER RECOVERY (DR)
============================================================

Definition : Disaster Recovery is the process and architecture used to restore application availability after a major failure.
Why Needed : • Protects against regional or infrastructure-level failures.
             • Reduces business downtime during disasters.

Interview : "DR is about keeping the application recoverable and available when the primary environment has a major failure."


============================================================
17. RECOVERY
============================================================

Definition : Recovery is the process of restoring services, infrastructure or data after a failure.
Why Needed : • Brings the application back to an operational state.
             • Helps meet defined RTO and RPO requirements.

RTO → Maximum acceptable downtime.
RPO → Maximum acceptable data loss.

Interview : "Recovery is the actual process of bringing the workload back after a failure, based on RTO and RPO requirements."


============================================================
18. HIGH AVAILABILITY (HA) vs DR vs BACKUP
============================================================

HA       → Prevent/reduce downtime during component failure.
Backup   → Recover lost/corrupted data.
DR       → Recover application/environment after major failure.

Example:
VM Failure          → HA / VM Scale Set
Deleted Data        → Backup
Azure Region Failure → DR

24. RESOURCE MODULE vs DATA MODULE
============================================================

RESOURCE MODULE
Definition : Module primarily designed to create/manage infrastructure resources.
Example    : VNet module → creates VNet, subnets, NSGs.

DATA SOURCE
Definition : Reads information about an already existing resource.
Example    : data "azurerm_resource_group" → reads existing RG.

Interview:
"Resource configuration creates infrastructure, whereas a data source reads existing infrastructure."

============================================================
31. TERRAFORM FOR_EACH
============================================================

Definition : for_each is a meta-argument used to create multiple resource instances from a map or set.
Why Needed : • Better when each resource needs a unique key or configuration.
             • Makes individual instances easier to manage.

Interview : "I prefer for_each when resources have unique configurations or keys instead of simply creating a fixed number."


============================================================
32. COUNT vs FOR_EACH
============================================================

COUNT
→ Numeric index
→ count.index
→ Good for identical resources
→ Example: 3 VMs

FOR_EACH
→ Key-based
→ each.key / each.value
→ Good for uniquely configured resources
→ Example: web/app/db resources

Interview:
"If resources are identical and quantity is the main requirement, I can use count.
If each resource has its own configuration, I prefer for_each."

73. LIVENESS vs READINESS
============================================================

LIVENESS
→ Checks whether the container is still healthy.
→ Failure can cause container restart.

READINESS
→ Checks whether the application is ready to receive traffic.
→ Failure removes the Pod from service traffic.

Interview:
"Liveness tells Kubernetes whether the application should be restarted;
readiness tells Kubernetes whether the Pod should receive traffic."


============================================================
74. REQUEST vs LIMIT
============================================================

REQUEST
→ Resources guaranteed/used for scheduling decisions.

LIMIT
→ Maximum resource consumption allowed for the container.

Example:
CPU Request → 250m
CPU Limit   → 500m

Interview:
"Requests help Kubernetes schedule the Pod, while limits restrict maximum resource consumption."

Why Needed : • Separates applications or environments.
             • Helps organize and manage Kubernetes resources.

88. BASIC TERRAFORM INTERVIEW QUESTIONS
============================================================

Q1. What is Terraform?
→ Infrastructure as Code tool used to provision and manage infrastructure.

Q2. What is a provider?
→ Plugin that allows Terraform to communicate with a platform/API.

Q3. What is a resource?
→ Infrastructure object managed by Terraform.

Q4. What is a module?
→ Reusable Terraform configuration.

Q5. What is a data source?
→ Reads existing information without creating the resource.

Q6. What is Terraform state?
→ Mapping between Terraform configuration and real infrastructure.

Q7. Why use remote backend?
→ Centralized and shared state management.

Q8. What is terraform plan?
→ Preview of infrastructure changes.

Q9. What is terraform apply?
→ Executes infrastructure changes.

Q10. What is terraform destroy?
→ Removes resources managed by Terraform.

Q11. What is count?
→ Creates multiple resource instances using a number.

Q12. What is for_each?
→ Creates multiple instances using a map/set.

Q13. count vs for_each?
→ count = index based; for_each = key based.

Q14. What is lifecycle?
→ Controls resource creation/replacement/destruction behavior.

Q15. What is depends_on?
→ Explicit dependency between resources/modules.

Q16. What is drift?
→ Difference between actual infrastructure and Terraform-managed configuration/state.

Q17. What is terraform import?
→ Brings an existing resource under Terraform management.

Q18. Why use modules?
→ Reusability, standardization and maintainability.

Q19. Why use variables?
→ Avoid hardcoding and support different environments.

Q20. What is output?
→ Exposes useful values from Terraform configuration/modules.

Q21. What is Terraform lock file?
→ .terraform.lock.hcl records selected provider versions/checksums.

Q22. What is terraform init?
→ Initializes backend, providers and modules.

Q23. What is terraform validate?
→ Validates Terraform configuration structure/syntax.

Q24. What is Terraform dependency?
→ Relationship where one resource needs another resource first.

Q25. Implicit vs explicit dependency?
→ Implicit is inferred from references; explicit is defined using depends_on.

Q10. Why Azure Policy?

Q11. Management Group vs Subscription?

Q12. Tenant vs Management Group?
→ Tenant is identity boundary; Management Group is governance hierarchy.

90. DOCKER — INTERVIEW QUESTIONS

Q1. What is Docker?
→ Containerization platform for packaging and running applications.

Q2. Image vs Container?
→ Image = package/template; Container = running instance.

Q3. What is Dockerfile?

Q8. What is Docker Registry?

Q9. What is ACR?
→ Azure-managed private container registry.

Q10. How does AKS get image from ACR?
→ AKS is granted permission to pull images from ACR.

91. KUBERNETES — INTERVIEW QUESTIONS
============================================================

Q1. Why Pod if we already have a container?
→ Kubernetes manages Pods as the smallest deployable unit; a Pod provides the shared execution/network context for one or more containers.

Q2. Pod vs Container?
→ Container runs application process; Pod is Kubernetes deployment unit containing one or more containers.

Q3. Deployment vs ReplicaSet?
→ Deployment manages application rollout and ReplicaSets; ReplicaSet maintains Pod replicas.

Q4. Why Service?
→ Provides stable networking for changing Pod IPs.

Q5. ClusterIP vs NodePort vs LoadBalancer?
→ ClusterIP = internal; NodePort = node-level external port; LoadBalancer = external load-balancer integration.

Q6. ConfigMap vs Secret?
→ ConfigMap = non-sensitive configuration; Secret = sensitive configuration.

Q7. Liveness vs Readiness?
→ Liveness = restart decision; Readiness = traffic eligibility.

Q8. What happens when Pod dies?
→ Kubernetes creates a replacement if the workload's desired state requires it.

Q9. What is rolling deployment?
→ Gradually replaces old Pods with new Pods.

Q10. How do you rollback?
→ Roll back the Kubernetes Deployment to a previous revision.

Q11. What is Namespace?
→ Logical separation of Kubernetes resources.

Q12. What is Ingress?
→ HTTP/HTTPS routing into Kubernetes services.

Q13. What is Helm?
→ Kubernetes package manager using Charts.

Q14. What is Node?
→ Worker machine where Pods run.

Q15. What is Node Pool?
→ Group of nodes with similar configuration.

92. MOST IMPORTANT "SCENARIO" QUESTIONS
============================================================

Q: VM has no internet access. What do you check?
→ NSG → Route Table/UDR → NAT Gateway → Firewall → DNS → Network Watcher.

Q: VM needs secure SSH/RDP access without public IP?
→ Azure Bastion.

Q: VM needs outbound internet but should not have public IP?
→ NAT Gateway.

Q: Two VNets need private communication?
→ VNet Peering.

Q: Spoke needs on-premises connectivity through hub?
→ VNet Peering + Gateway Transit.

Q: Application needs HTTP path-based routing?
→ Application Gateway.

Q: Application needs protection against web attacks?
→ WAF.

Q: Centralized network traffic inspection?
→ Azure Firewall.

Q: Private access to Key Vault?
→ Private Endpoint + Private DNS Zone.

Q: Existing Azure resource needs Terraform management?
→ terraform import.

Q: Someone manually changed Terraform infrastructure?
→ Terraform drift.

Q: Need 3 identical resources?
→ count.

Q: Need multiple resources with unique configuration?
→ for_each.

Q: Need to prevent production resource deletion?
→ lifecycle.prevent_destroy.

Q: Need replacement before destroying old resource?
→ lifecycle.create_before_destroy.

Q: Need to ignore external change to an attribute?
→ lifecycle.ignore_changes.

Q: Need existing resource information but don't want to create it?
→ Terraform data source.

Q: Need reusable infrastructure code?
→ Terraform module.

Q: Application needs container deployment on Azure?
→ Docker → ACR → AKS.

Q: Pod keeps restarting?
→ Check liveness probe, logs, events, resource limits, application health.

Q: Pod is running but user cannot access application?
→ Check Service → Endpoints → Ingress → Network/NSG → Application Gateway if used.

Q: New application version is failing?
→ Check Deployment/Pods/logs → rollback to previous Deployment revision.

93. FINAL 30-SECOND INTERVIEW STORY
============================================================

"At the Azure level, I start with the tenant and management-group
hierarchy, then separate platform and workload subscriptions.
For networking, I use VNets and subnets for segmentation, NSGs
for basic traffic filtering, and centralized services such as
Azure Firewall where required. For application traffic I use
Application Gateway or Load Balancer depending on the traffic
layer. Private Endpoints and Private DNS provide private access
to PaaS services. For infrastructure automation, I use Terraform
with reusable modules, remote state, variables, data sources and
meta-arguments such as count, for_each and lifecycle. For
containerized applications, I build Docker images, push them to
Azure Container Registry, and deploy them to Azure Kubernetes
Service using Helm. Kubernetes then manages Pods, Services,
scaling, rolling updates and self-healing."
