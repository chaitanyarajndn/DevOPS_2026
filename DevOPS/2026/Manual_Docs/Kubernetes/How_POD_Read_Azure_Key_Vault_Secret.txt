POD WANTS TO READ A SECRET FROM AZURE KEY VAULT
════════════════════════════════════════════════════════════════════

1. POD STARTS
   → Pod is configured with a Kubernetes ServiceAccount.
   → Example: icms-backend-sa


2. WORKLOAD IDENTITY
   → AKS sees that this Pod is using the ServiceAccount.
   → AKS Workload Identity webhook provides an OIDC token to the Pod.


3. POD GETS OIDC TOKEN
   → The token is placed inside the Pod.
   → This token represents the Pod's Kubernetes ServiceAccount.


4. POD → MICROSOFT ENTRA ID
   → Pod sends the OIDC token to Microsoft Entra ID.
   → Pod is basically saying: "I am this AKS ServiceAccount."


5. ENTRA ID CHECKS THE TOKEN
   → Entra ID checks the token's Issuer, Subject, Audience and signature.
   → It also checks the Federated Credential configured on the Managed Identity.

   ┌───────────────────────────────────────────────────────────────┐
   │ HOW IS FEDERATED CREDENTIAL CONNECTED TO MANAGED IDENTITY?   │
   ├───────────────────────────────────────────────────────────────┤
   │                                                               │
   │  A. Create / use a User-assigned Managed Identity             │
   │     → Example: uami-icms                                     │
   │                                                               │
   │  B. Open Azure Portal                                         │
   │     → Managed Identity                                        │
   │     → uami-icms                                               │
   │     → Settings                                                │
   │     → Federated credentials                                   │
   │                                                               │
   │  C. Create a Federated Credential THERE                       │
   │     → The credential is created on the Managed Identity.      │
   │                                                               │
   │  D. Configure:                                                 │
   │     → Issuer   = AKS OIDC Issuer URL                          │
   │     → Subject  = system:serviceaccount:<namespace>:<SA-name>  │
   │     → Audience = api://AzureADTokenExchange                   │
   │                                                               │
   │  E. This creates the trust:                                    │
   │                                                               │
   │     AKS ServiceAccount                                         │
   │            ↓                                                   │
   │     Federated Credential                                      │
   │            ↓                                                   │
   │     User-assigned Managed Identity                            │
   │                                                               │
   │  Meaning:                                                      │
   │  "If a token comes from this AKS OIDC issuer, for this          │
   │   specific ServiceAccount and audience, allow it to use         │
   │   this Managed Identity."                                      │
   │                                                               │
   └───────────────────────────────────────────────────────────────┘

   → If the token matches this configuration, Entra ID trusts the request.


6. ENTRA ID → MANAGED IDENTITY
   → Token matches the Federated Credential.
   → Entra ID accepts the request and issues an Azure access token for the Managed Identity.


7. CSI DRIVER STARTS THE KEY VAULT REQUEST
   → Secrets Store CSI Driver uses this Azure access to request the required secret.
   → SecretProviderClass tells the CSI Driver which Key Vault and which secret to request.


8. CSI DRIVER → AZURE KEY VAULT
   → CSI Driver sends the request to Key Vault using the Azure access token.
   → Key Vault checks the Managed Identity's RBAC permission.


9. KEY VAULT RETURNS THE SECRET
   → RBAC allows the request.
   → Key Vault returns the requested secret to the CSI Driver.


10. CSI DRIVER → POD
    → CSI Driver receives the secret.
    → It writes the secret into the mounted location inside the Pod.


11. SECRET AVAILABLE INSIDE POD
    → The secret is now available at:

       /mnt/secrets-store/DB_CONNECTION_STRING
